WebdriverIO के [Browser Runner](/docs/runner#browser-runner) के साथ आप एक वास्तविक डेस्कटॉप या मोबाइल ब्राउज़र में टेस्ट चला सकते हैं, और पेज पर जो कुछ रेंडर होता है उसे ऑटोमेट करने और उसके साथ इंटरैक्ट करने के लिए WebdriverIO और WebDriver प्रोटोकॉल का उपयोग कर सकते हैं। इस दृष्टिकोण के उन अन्य टेस्ट फ्रेमवर्क की तुलना में [कई फायदे](/docs/runner#browser-runner) हैं जो केवल [JSDOM](https://www.npmjs.com/package/jsdom) के विरुद्ध टेस्टिंग की अनुमति देते हैं।

## ब्राउज़र सपोर्ट

ब्राउज़र रनर टेस्ट बंडल को ब्राउज़र में एक्ज़ीक्यूट करता है। वह बंडल Chrome 90, Edge 90, Firefox 90 और Safari 14.1 में, तथा इन ब्राउज़रों के बाद के संस्करणों में चलता है।

एंड-टू-एंड टेस्ट Node.js में चलते हैं। इसके बजाय [`browser.execute`](/docs/api/browser/execute) को पास किया गया कोड ऑटोमेटेड ब्राउज़र में चलता है, जो ऊपर दिए गए संस्करणों से पुराना हो सकता है। उस कोड को ES2021 पर ही रखें।

## यह कैसे काम करता है?

Browser Runner एक टेस्ट पेज रेंडर करने और ब्राउज़र में आपके टेस्ट चलाने के लिए एक टेस्ट फ्रेमवर्क को इनिशियलाइज़ करने हेतु [Vite](https://vitejs.dev/) का उपयोग करता है। वर्तमान में यह केवल Mocha को सपोर्ट करता है, लेकिन Jasmine और Cucumber [रोडमैप पर](https://github.com/orgs/webdriverio/projects/1) हैं। यह उन प्रोजेक्ट्स के लिए भी किसी भी प्रकार के कंपोनेंट्स को टेस्ट करने की अनुमति देता है जो Vite का उपयोग नहीं करते।

Vite सर्वर WebdriverIO टेस्टरनर द्वारा शुरू किया जाता है और इस तरह कॉन्फ़िगर किया जाता है कि आप सभी रिपोर्टर और सर्विसेज़ का उपयोग वैसे ही कर सकें जैसे आप सामान्य e2e टेस्ट के लिए करते थे। इसके अलावा यह एक [`browser`](/docs/api/browser) इंस्टेंस इनिशियलाइज़ करता है जो आपको पेज पर किसी भी एलिमेंट के साथ इंटरैक्ट करने के लिए [WebdriverIO API](/docs/api) के एक सबसेट तक पहुँचने की अनुमति देता है। e2e टेस्ट की तरह ही, [`injectGlobals`](/docs/api/globals) कैसे सेट है उसके आधार पर, आप उस इंस्टेंस को ग्लोबल स्कोप से जुड़े `browser` वेरिएबल के माध्यम से या `@wdio/globals` से इम्पोर्ट करके एक्सेस कर सकते हैं।

WebdriverIO में निम्नलिखित फ्रेमवर्क के लिए बिल्ट-इन सपोर्ट है:

- [__Nuxt__](https://nuxt.com/): WebdriverIO का टेस्टरनर Nuxt एप्लिकेशन का पता लगाता है और स्वचालित रूप से आपके प्रोजेक्ट के composables सेट अप करता है तथा Nuxt बैकएंड को मॉक करने में मदद करता है, अधिक जानकारी के लिए [Nuxt docs](/docs/component-testing/vue#testing-vue-components-in-nuxt) पढ़ें
- [__TailwindCSS__](https://tailwindcss.com/): WebdriverIO का टेस्टरनर पता लगाता है कि क्या आप TailwindCSS का उपयोग कर रहे हैं और एनवायरनमेंट को टेस्ट पेज में ठीक से लोड करता है

## सेटअप

ब्राउज़र में यूनिट या कंपोनेंट टेस्टिंग के लिए WebdriverIO सेट अप करने हेतु, इसके माध्यम से एक नया WebdriverIO प्रोजेक्ट शुरू करें:

```bash
npm init wdio@latest ./
# or
yarn create wdio ./
```

कॉन्फ़िगरेशन विज़ार्ड शुरू होने पर, यूनिट और कंपोनेंट टेस्टिंग चलाने के लिए `browser` चुनें और चाहें तो किसी एक प्रीसेट को चुनें, अन्यथा यदि आप केवल बुनियादी यूनिट टेस्ट चलाना चाहते हैं तो _"Other"_ चुनें। यदि आप पहले से ही अपने प्रोजेक्ट में Vite का उपयोग करते हैं, तो आप एक कस्टम Vite कॉन्फ़िगरेशन भी कॉन्फ़िगर कर सकते हैं। अधिक जानकारी के लिए सभी [रनर विकल्प](/docs/runner#runner-options) देखें।

:::info

__नोट:__ WebdriverIO डिफ़ॉल्ट रूप से CI में ब्राउज़र टेस्ट headless मोड में चलाएगा, जैसे जब `CI` एनवायरनमेंट वेरिएबल `'1'` या `'true'` पर सेट हो। आप रनर के लिए [`headless`](/docs/runner#headless) विकल्प का उपयोग करके इस व्यवहार को मैन्युअल रूप से कॉन्फ़िगर कर सकते हैं।

:::

इस प्रक्रिया के अंत में आपको एक `wdio.conf.js` मिलनी चाहिए जिसमें विभिन्न WebdriverIO कॉन्फ़िगरेशन शामिल हैं, जिनमें एक `runner` प्रॉपर्टी भी है, उदाहरण के लिए:

```ts reference useHTTPS
https://github.com/webdriverio/example-recipes/blob/fd54f94306ed8e7b40f967739164dfe4d6d76b41/wdio.comp.conf.js
```

अलग-अलग [capabilities](/docs/configuration#capabilities) को परिभाषित करके आप अपने टेस्ट विभिन्न ब्राउज़रों में, चाहें तो समानांतर रूप से, चला सकते हैं।

यदि आप अभी भी अनिश्चित हैं कि सब कुछ कैसे काम करता है, तो WebdriverIO में कंपोनेंट टेस्टिंग के साथ शुरुआत करने के बारे में निम्नलिखित ट्यूटोरियल देखें:

## टेस्ट हार्नेस

यह पूरी तरह से आप पर निर्भर है कि आप अपने टेस्ट में क्या चलाना चाहते हैं और कंपोनेंट्स को कैसे रेंडर करना चाहते हैं। हालाँकि हम यूटिलिटी फ्रेमवर्क के रूप में [Testing Library](https://testing-library.com/) का उपयोग करने की सलाह देते हैं क्योंकि यह React, Preact, Svelte और Vue जैसे विभिन्न कंपोनेंट फ्रेमवर्क के लिए प्लगइन्स प्रदान करता है। यह कंपोनेंट्स को टेस्ट पेज में रेंडर करने के लिए बहुत उपयोगी है और हर टेस्ट के बाद इन कंपोनेंट्स को स्वचालित रूप से साफ़ कर देता है।

आप अपनी इच्छानुसार Testing Library प्रिमिटिव्स को WebdriverIO कमांड्स के साथ मिला सकते हैं, उदाहरण के लिए:

```js reference useHTTPS
https://github.com/webdriverio/example-recipes/blob/fd54f94306ed8e7b40f967739164dfe4d6d76b41/component-testing/svelte-example.js
```

__नोट:__ Testing Library के render मेथड्स का उपयोग करने से टेस्ट के बीच बनाए गए कंपोनेंट्स को हटाने में मदद मिलती है। यदि आप Testing Library का उपयोग नहीं करते हैं, तो सुनिश्चित करें कि आप अपने टेस्ट कंपोनेंट्स को एक ऐसे कंटेनर से जोड़ें जो टेस्ट के बीच साफ़ हो जाता है।

## सेटअप स्क्रिप्ट्स

आप Node.js में या ब्राउज़र में मनचाही स्क्रिप्ट्स चलाकर अपने टेस्ट सेट अप कर सकते हैं, जैसे स्टाइल्स इंजेक्ट करना, ब्राउज़र APIs को मॉक करना या किसी थर्ड पार्टी सर्विस से कनेक्ट करना। Node.js में कोड चलाने के लिए WebdriverIO [hooks](/docs/configuration#hooks) का उपयोग किया जा सकता है, जबकि [`mochaOpts.require`](/docs/frameworks#require) आपको टेस्ट लोड होने से पहले ब्राउज़र में स्क्रिप्ट्स इम्पोर्ट करने की अनुमति देता है, उदाहरण के लिए:

```js wdio.conf.js
export const config = {
    // ...
    mochaOpts: {
        ui: 'tdd',
        // ब्राउज़र में चलाने के लिए एक सेटअप स्क्रिप्ट प्रदान करें
        require: './__fixtures__/setup.js'
    },
    before: () => {
        // Node.js में टेस्ट एनवायरनमेंट सेट अप करें
    }
    // ...
}
```

उदाहरण के लिए, यदि आप निम्नलिखित सेटअप स्क्रिप्ट के साथ अपने टेस्ट में सभी [`fetch()`](https://developer.mozilla.org/en-US/docs/Web/API/fetch) कॉल्स को मॉक करना चाहते हैं:

```js ./fixtures/setup.js
import { fn } from '@wdio/browser-runner'

// सभी टेस्ट लोड होने से पहले कोड चलाएँ
window.fetch = fn()

export const mochaGlobalSetup = () => {
    // टेस्ट फ़ाइल लोड होने के बाद कोड चलाएँ
}

export const mochaGlobalTeardown = () => {
    // spec फ़ाइल एक्ज़ीक्यूट होने के बाद कोड चलाएँ
}

```

अब अपने टेस्ट में आप सभी ब्राउज़र रिक्वेस्ट्स के लिए कस्टम रिस्पॉन्स वैल्यूज़ प्रदान कर सकते हैं। ग्लोबल फिक्स्चर्स के बारे में अधिक जानकारी [Mocha docs](https://mochajs.org/#global-fixtures) में पढ़ें।

## टेस्ट और एप्लिकेशन फ़ाइलों को वॉच करें

आप अपने ब्राउज़र टेस्ट को कई तरीकों से डिबग कर सकते हैं। सबसे आसान तरीका है WebdriverIO टेस्टरनर को `--watch` फ़्लैग के साथ शुरू करना, उदाहरण के लिए:

```sh
$ npx wdio run ./wdio.conf.js --watch
```

यह शुरू में सभी टेस्ट चलाएगा और सभी के चलने के बाद रुक जाएगा। फिर आप अलग-अलग फ़ाइलों में बदलाव कर सकते हैं, जो फिर अलग-अलग दोबारा चलाई जाएँगी। यदि आप अपनी एप्लिकेशन फ़ाइलों की ओर इंगित करता हुआ [`filesToWatch`](/docs/configuration#filestowatch) सेट करते हैं, तो आपके ऐप में बदलाव किए जाने पर यह सभी टेस्ट दोबारा चलाएगा।

## डिबगिंग

हालाँकि अपने IDE में ब्रेकपॉइंट्स सेट करना और उन्हें रिमोट ब्राउज़र द्वारा पहचाना जाना (अभी तक) संभव नहीं है, फिर भी आप किसी भी बिंदु पर टेस्ट को रोकने के लिए [`debug`](/docs/api/browser/debug) कमांड का उपयोग कर सकते हैं। इससे आप DevTools खोलकर [sources टैब](https://buddy.works/tutorials/debugging-javascript-efficiently-with-chrome-devtools) में ब्रेकपॉइंट्स सेट करके टेस्ट को डिबग कर सकते हैं।

जब `debug` कमांड कॉल किया जाता है, तो आपको अपने टर्मिनल में एक Node.js repl इंटरफ़ेस भी मिलेगा, जिसमें लिखा होगा:

```
The execution has stopped!
You can now go into the browser or use the command line as REPL
(To exit, press ^C again or type .exit)
```

टेस्ट जारी रखने के लिए `Ctrl` या `Command` + `c` दबाएँ या `.exit` दर्ज करें।

## Selenium Grid का उपयोग करके चलाएँ

यदि आपने एक [Selenium Grid](https://www.selenium.dev/documentation/grid/) सेट अप किया है और अपना ब्राउज़र उस ग्रिड के माध्यम से चलाते हैं, तो आपको `host` ब्राउज़र रनर विकल्प सेट करना होगा ताकि ब्राउज़र उस सही होस्ट तक पहुँच सके जहाँ टेस्ट फ़ाइलें सर्व की जा रही हैं, उदाहरण के लिए:

```ts title=wdio.conf.ts
export const config: WebdriverIO.Config = {
    runner: ['browser', {
        // उस मशीन का नेटवर्क IP जो WebdriverIO प्रोसेस चलाती है
        host: 'http://172.168.0.2'
    }]
}
```

यह सुनिश्चित करेगा कि ब्राउज़र उस सही सर्वर इंस्टेंस को खोले जो WebdriverIO टेस्ट चलाने वाले इंस्टेंस पर होस्ट किया गया है।

## उदाहरण

लोकप्रिय कंपोनेंट फ्रेमवर्क का उपयोग करके कंपोनेंट्स की टेस्टिंग के विभिन्न उदाहरण आप हमारी [example repository](https://github.com/webdriverio/component-testing-examples) में पा सकते हैं।
