जैसे-जैसे प्रोजेक्ट बढ़ते हैं, अनिवार्य रूप से अधिक से अधिक इंटीग्रेशन टेस्ट जोड़े जाते हैं। इससे बिल्ड का समय बढ़ता है और उत्पादकता धीमी हो जाती है।

इसे रोकने के लिए, आपको अपने टेस्ट समानांतर (parallel) में चलाने चाहिए। WebdriverIO पहले से ही प्रत्येक स्पेक (या Cucumber में _feature file_) को एक ही सेशन के भीतर समानांतर में टेस्ट करता है। सामान्य तौर पर, प्रति स्पेक फ़ाइल केवल एक ही फ़ीचर को टेस्ट करने का प्रयास करें। कोशिश करें कि एक फ़ाइल में न तो बहुत अधिक और न ही बहुत कम टेस्ट हों। (हालांकि, यहां कोई सुनहरा नियम नहीं है।)

एक बार जब आपके टेस्ट में कई स्पेक फ़ाइलें हो जाएं, तो आपको अपने टेस्ट एक साथ (concurrently) चलाना शुरू कर देना चाहिए। ऐसा करने के लिए, अपनी कॉन्फ़िग फ़ाइल में `maxInstances` प्रॉपर्टी को समायोजित करें। WebdriverIO आपको अधिकतम समवर्तीता (concurrency) के साथ अपने टेस्ट चलाने की अनुमति देता है—जिसका अर्थ है कि चाहे आपके पास कितनी भी फ़ाइलें और टेस्ट हों, वे सभी समानांतर में चल सकते हैं। (यह अभी भी कुछ सीमाओं के अधीन है, जैसे आपके कंप्यूटर का CPU, समवर्तीता प्रतिबंध, आदि।)

> मान लीजिए आपके पास 3 अलग-अलग capabilities (Chrome, Firefox, और Safari) हैं और आपने `maxInstances` को `1` पर सेट किया है। WDIO टेस्ट रनर 3 प्रोसेस शुरू करेगा। इसलिए, यदि आपके पास 10 स्पेक फ़ाइलें हैं और आप `maxInstances` को `10` पर सेट करते हैं, तो _सभी_ स्पेक फ़ाइलें एक साथ टेस्ट की जाएंगी, और 30 प्रोसेस शुरू होंगे।

आप सभी ब्राउज़रों के लिए एट्रिब्यूट सेट करने हेतु `maxInstances` प्रॉपर्टी को ग्लोबल रूप से परिभाषित कर सकते हैं।

यदि आप अपना स्वयं का WebDriver ग्रिड चलाते हैं, तो आपके पास (उदाहरण के लिए) एक ब्राउज़र के लिए दूसरे की तुलना में अधिक क्षमता हो सकती है। उस स्थिति में, आप अपने capability ऑब्जेक्ट में `maxInstances` को _सीमित_ कर सकते हैं:

```js
// wdio.conf.js
export const config = {
    // ...
    // सभी ब्राउज़र के लिए maxInstance सेट करें
    maxInstances: 10,
    // ...
    capabilities: [{
        browserName: 'firefox'
    }, {
        // maxInstances को प्रति capability ओवरराइट किया जा सकता है। इसलिए यदि आपके पास एक इन-हाउस WebDriver
        // ग्रिड है जिसमें केवल 5 firefox इंस्टेंस उपलब्ध हैं, तो आप सुनिश्चित कर सकते हैं कि एक समय में
        // 5 से अधिक इंस्टेंस शुरू न हों।
        browserName: 'chrome'
    }],
    // ...
}
```

## मुख्य कॉन्फ़िग फ़ाइल से इनहेरिट करें

यदि आप अपना टेस्ट सूट कई वातावरणों (जैसे, dev और integration) में चलाते हैं, तो चीज़ों को प्रबंधनीय रखने के लिए कई कॉन्फ़िगरेशन फ़ाइलों का उपयोग करना मददगार हो सकता है।

[पेज ऑब्जेक्ट अवधारणा](pageobjects) के समान, सबसे पहले आपको एक मुख्य कॉन्फ़िग फ़ाइल की आवश्यकता होगी। इसमें वे सभी कॉन्फ़िगरेशन होते हैं जिन्हें आप सभी वातावरणों में साझा करते हैं।

फिर प्रत्येक वातावरण के लिए एक अन्य कॉन्फ़िग फ़ाइल बनाएं, और मुख्य कॉन्फ़िग को वातावरण-विशिष्ट कॉन्फ़िग के साथ पूरक करें:

```js
// wdio.dev.config.js
import { deepmerge } from 'deepmerge-ts'
import wdioConf from './wdio.conf.js'

// मुख्य कॉन्फ़िग फ़ाइल को डिफ़ॉल्ट के रूप में रखें लेकिन वातावरण विशिष्ट जानकारी को ओवरराइट करें
export const config = deepmerge(wdioConf.config, {
    capabilities: [
        // अधिक caps यहां परिभाषित करें
        // ...
    ],

    // लोकल के बजाय sauce पर टेस्ट चलाएं
    user: process.env.SAUCE_USERNAME,
    key: process.env.SAUCE_ACCESS_KEY,
    services: ['sauce']
}, { clone: false })

// एक अतिरिक्त रिपोर्टर जोड़ें
config.reporters.push('allure')
```

## टेस्ट स्पेक्स को सूट में समूहित करना

आप टेस्ट स्पेक्स को सूट में समूहित कर सकते हैं और सभी के बजाय केवल विशिष्ट सूट चला सकते हैं।

सबसे पहले, अपने WDIO कॉन्फ़िग में अपने सूट परिभाषित करें:

```js
// wdio.conf.js
export const config = {
    // सभी टेस्ट परिभाषित करें
    specs: ['./test/specs/**/*.spec.js'],
    // ...
    // विशिष्ट सूट परिभाषित करें
    suites: {
        login: [
            './test/specs/login.success.spec.js',
            './test/specs/login.failure.spec.js'
        ],
        otherFeature: [
            // ...
        ]
    },
    // ...
}
```

अब, यदि आप केवल एक सूट चलाना चाहते हैं, तो आप सूट का नाम CLI आर्ग्युमेंट के रूप में पास कर सकते हैं:

```sh
wdio wdio.conf.js --suite login
```

या, एक साथ कई सूट चलाएं:

```sh
wdio wdio.conf.js --suite login --suite otherFeature
```

## टेस्ट स्पेक्स को क्रमिक रूप से चलाने के लिए समूहित करना

जैसा कि ऊपर बताया गया है, टेस्ट को एक साथ चलाने के लाभ हैं। हालांकि, कुछ ऐसे मामले हैं जहां टेस्ट को एक ही इंस्टेंस में क्रमिक रूप से चलाने के लिए एक साथ समूहित करना फायदेमंद होगा। इसके उदाहरण मुख्य रूप से वे हैं जहां सेटअप की लागत बड़ी होती है, जैसे कोड को ट्रांसपाइल करना या क्लाउड इंस्टेंस प्रोविज़न करना, लेकिन कुछ उन्नत उपयोग मॉडल भी हैं जो इस क्षमता से लाभान्वित होते हैं।

टेस्ट को एक ही इंस्टेंस में चलाने के लिए समूहित करने हेतु, उन्हें specs परिभाषा के भीतर एक array के रूप में परिभाषित करें।

```json
    "specs": [
        [
            "./test/specs/test_login.js",
            "./test/specs/test_product_order.js",
            "./test/specs/test_checkout.js"
        ],
        "./test/specs/test_b*.js",
    ],
```
ऊपर दिए गए उदाहरण में, टेस्ट 'test_login.js', 'test_product_order.js' और 'test_checkout.js' एक ही इंस्टेंस में क्रमिक रूप से चलाए जाएंगे और प्रत्येक "test_b*" टेस्ट अलग-अलग इंस्टेंस में एक साथ चलेंगे।

सूट में परिभाषित स्पेक्स को समूहित करना भी संभव है, इसलिए अब आप सूट को इस तरह भी परिभाषित कर सकते हैं:
```json
    "suites": {
        end2end: [
            [
                "./test/specs/test_login.js",
                "./test/specs/test_product_order.js",
                "./test/specs/test_checkout.js"
            ]
        ],
        allb: ["./test/specs/test_b*.js"]
},
```
और इस स्थिति में "end2end" सूट के सभी टेस्ट एक ही इंस्टेंस में चलाए जाएंगे।

किसी पैटर्न का उपयोग करके टेस्ट को क्रमिक रूप से चलाने पर, यह स्पेक फ़ाइलों को वर्णानुक्रम (alphabetical order) में चलाएगा

```json
  "suites": {
    end2end: ["./test/specs/test_*.js"]
  },
```

यह ऊपर दिए गए पैटर्न से मेल खाने वाली फ़ाइलों को निम्नलिखित क्रम में चलाएगा:

```
  [
      "./test/specs/test_checkout.js",
      "./test/specs/test_login.js",
      "./test/specs/test_product_order.js"
  ]
```

## चयनित टेस्ट चलाएं

कुछ मामलों में, आप अपने सूट का केवल एक टेस्ट (या टेस्ट का एक उपसमूह) निष्पादित करना चाह सकते हैं।

`--spec` पैरामीटर के साथ, आप निर्दिष्ट कर सकते हैं कि कौन सा _suite_ (Mocha, Jasmine) या _feature_ (Cucumber) चलाया जाना चाहिए। पाथ आपकी वर्तमान वर्किंग डायरेक्टरी के सापेक्ष (relative) रिज़ॉल्व किया जाता है।

उदाहरण के लिए, केवल अपना लॉगिन टेस्ट चलाने के लिए:

```sh
wdio wdio.conf.js --spec ./test/specs/e2e/login.js
```

या एक साथ कई स्पेक्स चलाएं:

```sh
wdio wdio.conf.js --spec ./test/specs/signup.js --spec ./test/specs/forgot-password.js
```

यदि `--spec` मान किसी विशेष स्पेक फ़ाइल की ओर इंगित नहीं करता है, तो इसके बजाय इसका उपयोग आपके कॉन्फ़िगरेशन में परिभाषित स्पेक फ़ाइल नामों को फ़िल्टर करने के लिए किया जाता है।

स्पेक फ़ाइल नामों में "dialog" शब्द वाले सभी स्पेक्स चलाने के लिए, आप इसका उपयोग कर सकते हैं:

```sh
wdio wdio.conf.js --spec dialog
```

ध्यान दें कि प्रत्येक टेस्ट फ़ाइल एक ही टेस्ट रनर प्रोसेस में चल रही है। चूंकि हम फ़ाइलों को पहले से स्कैन नहीं करते हैं (`wdio` में फ़ाइल नाम पाइप करने की जानकारी के लिए अगला अनुभाग देखें), आप Mocha को केवल उस सूट को चलाने का निर्देश देने के लिए अपनी स्पेक फ़ाइल के शीर्ष पर (उदाहरण के लिए) `describe.only` का उपयोग _नहीं_ कर सकते।

यह फ़ीचर आपको वही लक्ष्य प्राप्त करने में मदद करेगा।

जब `--spec` विकल्प प्रदान किया जाता है, तो यह कॉन्फ़िग `specs` या किसी capability के `wdio:specs` द्वारा परिभाषित किसी भी पैटर्न को ओवरराइड कर देगा।

## चयनित टेस्ट को बाहर करें

आवश्यकता होने पर, यदि आपको किसी रन से विशेष स्पेक फ़ाइल(फ़ाइलों) को बाहर करने की आवश्यकता है, तो आप `--exclude` पैरामीटर (Mocha, Jasmine) या feature (Cucumber) का उपयोग कर सकते हैं।

उदाहरण के लिए, अपने लॉगिन टेस्ट को टेस्ट रन से बाहर करने के लिए:

```sh
wdio wdio.conf.js --exclude ./test/specs/e2e/login.js
```

या, कई स्पेक फ़ाइलों को बाहर करें:

 ```sh
wdio wdio.conf.js --exclude ./test/specs/signup.js --exclude ./test/specs/forgot-password.js
```

या, किसी सूट का उपयोग करके फ़िल्टर करते समय किसी स्पेक फ़ाइल को बाहर करें:

```sh
wdio wdio.conf.js --suite login --exclude ./test/specs/e2e/login.js
```

यदि `--exclude` मान किसी विशेष स्पेक फ़ाइल की ओर इंगित नहीं करता है, तो इसके बजाय इसका उपयोग आपके कॉन्फ़िगरेशन में परिभाषित स्पेक फ़ाइल नामों को फ़िल्टर करने के लिए किया जाता है।

स्पेक फ़ाइल नामों में "dialog" शब्द वाले सभी स्पेक्स को बाहर करने के लिए, आप इसका उपयोग कर सकते हैं:

```sh
wdio wdio.conf.js --exclude dialog
```

### पूरे सूट को बाहर करें

आप नाम द्वारा पूरे सूट को भी बाहर कर सकते हैं। यदि बहिष्करण (exclusion) मान आपके कॉन्फ़िग में परिभाषित किसी सूट नाम से मेल खाता है और फ़ाइल पाथ जैसा नहीं दिखता है, तो पूरा सूट छोड़ दिया जाएगा:

```sh
wdio wdio.conf.js --suite login --suite checkout --exclude login
```

यह केवल `checkout` सूट चलाएगा, `login` सूट को पूरी तरह से छोड़ देगा।

मिश्रित बहिष्करण (सूट और स्पेक पैटर्न) अपेक्षा के अनुसार काम करते हैं:

```sh
wdio wdio.conf.js --suite login --exclude dialog --exclude signup
```

इस उदाहरण में, यदि `signup` एक परिभाषित सूट नाम है, तो उस सूट को बाहर कर दिया जाएगा। पैटर्न `dialog` उन सभी स्पेक फ़ाइलों को फ़िल्टर कर देगा जिनके फ़ाइल नाम में "dialog" है।

:::note
यदि आप `--suite X` और `--exclude X` दोनों निर्दिष्ट करते हैं, तो बहिष्करण को प्राथमिकता मिलती है और सूट `X` नहीं चलेगा।
:::

जब `--exclude` विकल्प प्रदान किया जाता है, तो यह कॉन्फ़िग `exclude` या किसी capability के `wdio:exclude` द्वारा परिभाषित किसी भी पैटर्न को ओवरराइड कर देगा।

## सूट और टेस्ट स्पेक्स चलाएं

व्यक्तिगत स्पेक्स के साथ एक पूरा सूट चलाएं।

```sh
wdio wdio.conf.js --suite login --spec ./test/specs/signup.js
```

## कई, विशिष्ट टेस्ट स्पेक्स चलाएं

कभी-कभी&mdash;कंटीन्यूअस इंटीग्रेशन के संदर्भ में और अन्यथा भी&mdash;चलाने के लिए स्पेक्स के कई सेट निर्दिष्ट करना आवश्यक होता है। WebdriverIO की `wdio` कमांड लाइन यूटिलिटी पाइप किए गए फ़ाइल नामों (`find`, `grep`, या अन्य से) को स्वीकार करती है।

पाइप किए गए फ़ाइल नाम कॉन्फ़िगरेशन की `spec` सूची में निर्दिष्ट globs या फ़ाइल नामों की सूची को ओवरराइड करते हैं।

```sh
grep -r -l --include "*.js" "myText" | wdio wdio.conf.js
```

_**नोट:** यह एकल स्पेक चलाने के लिए `--spec` फ़्लैग को_ ओवरराइड नहीं _करेगा।_

## MochaOpts के साथ विशिष्ट टेस्ट चलाना

आप wdio CLI में mocha विशिष्ट आर्ग्युमेंट `--mochaOpts.grep` पास करके यह भी फ़िल्टर कर सकते हैं कि आप कौन सा विशिष्ट `suite|describe` और/या `it|test` चलाना चाहते हैं।

```sh
wdio wdio.conf.js --mochaOpts.grep myText
wdio wdio.conf.js --mochaOpts.grep "Text with spaces"
```

_**नोट:** Mocha, WDIO टेस्ट रनर द्वारा इंस्टेंस बनाए जाने के बाद टेस्ट को फ़िल्टर करेगा, इसलिए आप कई इंस्टेंस को शुरू होते हुए देख सकते हैं लेकिन वास्तव में निष्पादित होते हुए नहीं।_

## MochaOpts के साथ विशिष्ट टेस्ट को बाहर करें

आप wdio CLI में mocha विशिष्ट आर्ग्युमेंट `--mochaOpts.invert` पास करके यह भी फ़िल्टर कर सकते हैं कि आप कौन सा विशिष्ट `suite|describe` और/या `it|test` बाहर करना चाहते हैं। `--mochaOpts.invert`, `--mochaOpts.grep` के विपरीत कार्य करता है

```sh
wdio wdio.conf.js --mochaOpts.grep "string|regex" --mochaOpts.invert
wdio wdio.conf.js --spec ./test/specs/e2e/login.js --mochaOpts.grep "string|regex" --mochaOpts.invert
```

_**नोट:** Mocha, WDIO टेस्ट रनर द्वारा इंस्टेंस बनाए जाने के बाद टेस्ट को फ़िल्टर करेगा, इसलिए आप कई इंस्टेंस को शुरू होते हुए देख सकते हैं लेकिन वास्तव में निष्पादित होते हुए नहीं।_

## विफलता के बाद टेस्टिंग रोकें

`bail` विकल्प के साथ, आप WebdriverIO को किसी भी टेस्ट के विफल होने के बाद टेस्टिंग रोकने के लिए कह सकते हैं।

यह बड़े टेस्ट सूट के साथ मददगार है जब आप पहले से जानते हैं कि आपका बिल्ड टूट जाएगा, लेकिन आप पूर्ण टेस्टिंग रन के लंबे इंतज़ार से बचना चाहते हैं।

`bail` विकल्प एक संख्या की अपेक्षा करता है, जो निर्दिष्ट करती है कि WebDriver द्वारा पूरे टेस्टिंग रन को रोकने से पहले कितनी टेस्ट विफलताएं हो सकती हैं। डिफ़ॉल्ट `0` है, जिसका अर्थ है कि यह हमेशा उन सभी टेस्ट स्पेक्स को चलाता है जो इसे मिल सकते हैं।

bail कॉन्फ़िगरेशन पर अतिरिक्त जानकारी के लिए कृपया [विकल्प पेज](configuration) देखें।
## रन विकल्पों का पदानुक्रम

कौन से स्पेक्स चलाने हैं, यह घोषित करते समय, एक निश्चित पदानुक्रम होता है जो परिभाषित करता है कि किस पैटर्न को प्राथमिकता मिलेगी। वर्तमान में, यह उच्चतम प्राथमिकता से निम्नतम तक इस प्रकार काम करता है:

> CLI `--spec` आर्ग्युमेंट > capability `wdio:specs` > config `specs`
> CLI `--exclude` आर्ग्युमेंट > config `exclude` > capability `wdio:exclude`

यदि केवल कॉन्फ़िग पैरामीटर दिया गया है, तो इसका उपयोग सभी capabilities के लिए किया जाएगा। हालांकि, यदि पैटर्न को capability स्तर पर परिभाषित किया गया है, तो कॉन्फ़िग पैटर्न के बजाय इसका उपयोग किया जाएगा। अंत में, कमांड लाइन पर परिभाषित कोई भी स्पेक पैटर्न दिए गए अन्य सभी पैटर्न को ओवरराइड कर देगा।

### capability-परिभाषित स्पेक पैटर्न का उपयोग करना

जब आप capability स्तर पर एक स्पेक पैटर्न परिभाषित करते हैं, तो यह कॉन्फ़िग स्तर पर परिभाषित किसी भी पैटर्न को ओवरराइड कर देगा। यह तब उपयोगी होता है जब अलग-अलग डिवाइस capabilities के आधार पर टेस्ट को अलग करने की आवश्यकता होती है। ऐसे मामलों में, कॉन्फ़िग स्तर पर एक सामान्य स्पेक पैटर्न और capability स्तर पर अधिक विशिष्ट पैटर्न का उपयोग करना अधिक उपयोगी होता है।

उदाहरण के लिए, मान लीजिए आपके पास दो डायरेक्टरी हैं, एक Android टेस्ट के लिए, और एक iOS टेस्ट के लिए।

आपकी कॉन्फ़िग फ़ाइल गैर-विशिष्ट डिवाइस टेस्ट के लिए पैटर्न को इस प्रकार परिभाषित कर सकती है:

```js
{
    specs: ['tests/general/**/*.js']
}
```

लेकिन फिर, आपके Android और iOS डिवाइसों के लिए अलग-अलग capabilities होंगी, जहां पैटर्न इस तरह दिख सकते हैं:

```json
{
  "platformName": "Android",
  "wdio:specs": [
    "tests/android/**/*.js"
  ]
}
```

```json
{
  "platformName": "iOS",
  "wdio:specs": [
    "tests/ios/**/*.js"
  ]
}
```

यदि आपको अपनी कॉन्फ़िग फ़ाइल में इन दोनों capabilities की आवश्यकता है, तो Android डिवाइस केवल "android" नेमस्पेस के अंतर्गत टेस्ट चलाएगा, और iOS केवल "ios" नेमस्पेस के अंतर्गत टेस्ट चलाएगा!

```js
//wdio.conf.js
export const config = {
    "specs": [
        "tests/general/**/*.js"
    ],
    "capabilities": [
        {
            platformName: "Android",
            "wdio:specs": ["tests/android/**/*.js"],
            //...
        },
        {
            platformName: "iOS",
            "wdio:specs": ["tests/ios/**/*.js"],
            //...
        },
        {
            platformName: "Chrome",
            //कॉन्फ़िग स्तर के specs का उपयोग किया जाएगा
        }
    ]
}
```
