आप WebdriverIO टेस्टरनर के साथ कुछ ऐसे टेस्ट को दोबारा चला सकते हैं जो फ्लेकी नेटवर्क या रेस कंडीशन जैसी चीज़ों के कारण अस्थिर साबित होते हैं। (हालांकि, यदि टेस्ट अस्थिर हो जाते हैं तो केवल रीरन दर बढ़ाने की अनुशंसा नहीं की जाती है!)

## Mocha में सूट को पुनः चलाएं

Mocha के संस्करण 3 से, आप पूरे टेस्ट सूट (एक `describe` ब्लॉक के अंदर सब कुछ) को दोबारा चला सकते हैं। यदि आप Mocha का उपयोग करते हैं तो आपको WebdriverIO कार्यान्वयन के बजाय इस रीट्राई तंत्र को प्राथमिकता देनी चाहिए, जो आपको केवल कुछ टेस्ट ब्लॉक (एक `it` ब्लॉक के भीतर सब कुछ) को दोबारा चलाने की अनुमति देता है। `this.retries()` मेथड का उपयोग करने के लिए, सूट ब्लॉक `describe` को फैट एरो फ़ंक्शन `() => {}` के बजाय एक अनबाउंड फ़ंक्शन `function(){}` का उपयोग करना चाहिए, जैसा कि [Mocha docs](https://mochajs.org/#arrow-functions) में वर्णित है। Mocha का उपयोग करके आप अपनी `wdio.conf.js` में `mochaOpts.retries` का उपयोग करके सभी specs के लिए रीट्राई काउंट भी सेट कर सकते हैं।

यहां एक उदाहरण है:

```js
describe('retries', function () {
    // इस सूट के सभी टेस्ट को अधिकतम 4 बार पुनः चलाएं
    this.retries(4)

    beforeEach(async () => {
        await browser.url('http://www.yahoo.com')
    })

    it('should succeed on the 3rd try', async function () {
        // इस टेस्ट को केवल अधिकतम 2 बार पुनः चलाने के लिए निर्दिष्ट करें
        this.retries(2)
        console.log('run')
        await expect($('.foo')).toBeDisplayed()
    })
})
```

## Jasmine या Mocha में एकल टेस्ट को पुनः चलाएं

किसी विशिष्ट टेस्ट ब्लॉक को दोबारा चलाने के लिए आप टेस्ट ब्लॉक फ़ंक्शन के बाद अंतिम पैरामीटर के रूप में रीरन की संख्या लागू कर सकते हैं:

<Tabs
  defaultValue="mocha"
  values={[
    {label: 'Mocha', value: 'mocha'},
    {label: 'Jasmine', value: 'jasmine'},
  ]
}>
<TabItem value="mocha">

```js
describe('my flaky app', () => {
    /**
     * spec जो अधिकतम 4 बार चलता है (1 वास्तविक रन + 3 रीरन)
     */
    it('should rerun a test at least 3 times', async function () {
        console.log(this.wdioRetries) // रीट्राई की संख्या लौटाता है
        // ...
    }, 3)
})
```

यही हुक्स के लिए भी काम करता है:

```js
describe('my flaky app', () => {
    /**
     * हुक जो अधिकतम 2 बार चलता है (1 वास्तविक रन + 1 रीरन)
     */
    beforeEach(async () => {
        // ...
    }, 1)

    // ...
})
```

</TabItem>
<TabItem value="jasmine">

```js
describe('my flaky app', () => {
    /**
     * spec जो अधिकतम 4 बार चलता है (1 वास्तविक रन + 3 रीरन)
     */
    it('should rerun a test at least 3 times', async function () {
        console.log(this.wdioRetries) // रीट्राई की संख्या लौटाता है
        // ...
    }, jasmine.DEFAULT_TIMEOUT_INTERVAL, 3)

```

यही हुक्स के लिए भी काम करता है:

```js
describe('my flaky app', () => {
    /**
     * हुक जो अधिकतम 2 बार चलता है (1 वास्तविक रन + 1 रीरन)
     */
    beforeEach(async () => {
        // ...
    }, jasmine.DEFAULT_TIMEOUT_INTERVAL, 1)

    // ...
})
```

यदि आप Jasmine का उपयोग कर रहे हैं, तो दूसरा पैरामीटर टाइमआउट के लिए आरक्षित है। रीट्राई पैरामीटर लागू करने के लिए आपको टाइमआउट को उसके डिफ़ॉल्ट मान `jasmine.DEFAULT_TIMEOUT_INTERVAL` पर सेट करना होगा और फिर अपना रीट्राई काउंट लागू करना होगा।

</TabItem>
</Tabs>

यह रीट्राई तंत्र केवल एकल हुक्स या टेस्ट ब्लॉक को पुनः चलाने की अनुमति देता है। यदि आपके टेस्ट के साथ आपके एप्लिकेशन को सेट अप करने के लिए कोई हुक है, तो वह हुक नहीं चलाया जाता है। [Mocha प्रदान करता है](https://mochajs.org/#retry-tests) नेटिव टेस्ट रीट्राई जो यह व्यवहार प्रदान करते हैं, जबकि Jasmine नहीं करता। आप `afterTest` हुक में निष्पादित रीट्राई की संख्या तक पहुंच सकते हैं।

## Cucumber में पुनः चलाना

### Cucumber में पूरे सूट को पुनः चलाएं

cucumber >=6 के लिए आप [`retry`](https://github.com/cucumber/cucumber-js/blob/master/docs/cli.md#retry-failing-tests) कॉन्फ़िगरेशन विकल्प के साथ एक वैकल्पिक पैरामीटर `retryTagFilter` प्रदान कर सकते हैं, ताकि आपके सभी या कुछ विफल होने वाले परिदृश्यों को सफल होने तक अतिरिक्त रीट्राई मिल सकें। इस सुविधा के काम करने के लिए आपको `scenarioLevelReporter` को `true` पर सेट करना होगा।

### Cucumber में Step Definitions को पुनः चलाएं

किसी विशिष्ट step definition के लिए रीरन दर परिभाषित करने के लिए बस उस पर एक retry विकल्प लागू करें, जैसे:

```js
export default function () {
    /**
     * step definition जो अधिकतम 3 बार चलती है (1 वास्तविक रन + 2 रीरन)
     */
    this.Given(/^some step definition$/, { wrapperOptions: { retry: 2 } }, async () => {
        // ...
    })
    // ...
})
```

रीरन केवल आपकी step definitions फ़ाइल में परिभाषित किए जा सकते हैं, कभी भी आपकी feature फ़ाइल में नहीं।

## प्रति-specfile आधार पर रीट्राई जोड़ें

पहले, केवल टेस्ट- और सूट-स्तरीय रीट्राई उपलब्ध थे, जो अधिकांश मामलों में ठीक हैं।

लेकिन किसी भी ऐसे टेस्ट में जिसमें स्टेट शामिल होती है (जैसे किसी सर्वर या डेटाबेस में), पहली टेस्ट विफलता के बाद स्टेट अमान्य रह सकती है। अमान्य स्टेट के कारण, जिससे वे शुरू होंगे, बाद के किसी भी रीट्राई के पास होने की कोई संभावना नहीं हो सकती है।

प्रत्येक specfile के लिए एक नया `browser` इंस्टेंस बनाया जाता है, जो इसे किसी भी अन्य स्टेट (सर्वर, डेटाबेस) को हुक और सेटअप करने के लिए एक आदर्श स्थान बनाता है। इस स्तर पर रीट्राई का अर्थ है कि पूरी सेटअप प्रक्रिया बस दोहराई जाएगी, ठीक वैसे ही जैसे कि यह किसी नई specfile के लिए हो।

```js title="wdio.conf.js"
export const config = {
    // ...
    /**
     * पूरी specfile के समग्र रूप से विफल होने पर उसे पुनः चलाने की संख्या
     */
    specFileRetries: 1,
    /**
     * spec फ़ाइल रीट्राई प्रयासों के बीच सेकंड में विलंब
     */
    specFileRetriesDelay: 0,
    /**
     * पुनः चलाई गई specfiles को कतार की शुरुआत में डाला जाता है और तुरंत पुनः चलाया जाता है
     */
    specFileRetriesDeferred: false
}
```

## किसी विशिष्ट टेस्ट को कई बार चलाएं

यह कोडबेस में फ्लेकी टेस्ट को शामिल होने से रोकने में मदद करने के लिए है। `--repeat` cli विकल्प जोड़ने से यह निर्दिष्ट specs या suites को N बार चलाएगा। इस cli फ़्लैग का उपयोग करते समय `--spec` या `--suite` फ़्लैग भी निर्दिष्ट किया जाना चाहिए।

कोडबेस में नए टेस्ट जोड़ते समय, विशेष रूप से CI/CD प्रक्रिया के माध्यम से, टेस्ट पास होकर मर्ज हो सकते हैं लेकिन बाद में फ्लेकी हो सकते हैं। यह फ्लेकीनेस कई चीज़ों से आ सकती है जैसे नेटवर्क समस्याएं, सर्वर लोड, डेटाबेस का आकार, आदि। अपनी CD/CD प्रक्रिया में `--repeat` फ़्लैग का उपयोग करने से इन फ्लेकी टेस्ट को मुख्य कोडबेस में मर्ज होने से पहले पकड़ने में मदद मिल सकती है।

एक रणनीति यह है कि अपनी CI/CD प्रक्रिया में अपने टेस्ट को सामान्य रूप से चलाएं, लेकिन यदि आप कोई नया टेस्ट जोड़ रहे हैं तो आप `--spec` में निर्दिष्ट नई spec के साथ `--repeat` का उपयोग करके टेस्ट का एक और सेट चला सकते हैं, ताकि यह नए टेस्ट को x बार चलाए। यदि टेस्ट इनमें से किसी भी बार विफल होता है तो टेस्ट मर्ज नहीं होगा और यह देखना होगा कि वह क्यों विफल हुआ।

```sh
# यह example.e2e.js spec को 5 बार चलाएगा
npx wdio run ./wdio.conf.js --spec example.e2e.js --repeat 5
```
