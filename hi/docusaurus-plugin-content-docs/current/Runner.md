WebdriverIO में एक रनर यह नियंत्रित करता है कि टेस्टरनर का उपयोग करते समय टेस्ट कैसे और कहाँ चलाए जाते हैं। WebdriverIO वर्तमान में दो अलग-अलग प्रकार के रनर का समर्थन करता है: लोकल और ब्राउज़र रनर।

## लोकल रनर

[लोकल रनर](https://www.npmjs.com/package/@wdio/local-runner) आपके फ्रेमवर्क (जैसे Mocha, Jasmine या Cucumber) को एक वर्कर प्रोसेस के भीतर शुरू करता है और आपकी सभी टेस्ट फ़ाइलों को आपके Node.js एनवायरनमेंट के भीतर चलाता है। अधिकतम समानांतरता (concurrency) के लिए प्रत्येक टेस्ट फ़ाइल प्रति कैपेबिलिटी एक अलग वर्कर प्रोसेस में चलाई जाती है। प्रत्येक वर्कर प्रोसेस एक ही ब्राउज़र इंस्टेंस का उपयोग करता है और इसलिए अधिकतम आइसोलेशन के लिए अपना स्वयं का ब्राउज़र सेशन चलाता है।

चूँकि प्रत्येक टेस्ट अपनी स्वयं की आइसोलेटेड प्रोसेस में चलाया जाता है, इसलिए टेस्ट फ़ाइलों के बीच डेटा साझा करना संभव नहीं है। इससे निपटने के दो तरीके हैं:

- सभी वर्कर्स के बीच डेटा साझा करने के लिए [`@wdio/shared-store-service`](https://www.npmjs.com/package/@wdio/shared-store-service) का उपयोग करें
- स्पेक फ़ाइलों को ग्रुप करें ([टेस्ट सूट को व्यवस्थित करना](https://webdriver.io/docs/organizingsuites#grouping-test-specs-to-run-sequentially) में और पढ़ें)

यदि `wdio.conf.js` में कुछ और परिभाषित नहीं किया गया है, तो लोकल रनर WebdriverIO में डिफ़ॉल्ट रनर है।

### इंस्टॉल करें

लोकल रनर का उपयोग करने के लिए आप इसे इस प्रकार इंस्टॉल कर सकते हैं:

```sh
npm install --save-dev @wdio/local-runner
```

### सेटअप

लोकल रनर WebdriverIO में डिफ़ॉल्ट रनर है, इसलिए इसे अपनी `wdio.conf.js` में परिभाषित करने की आवश्यकता नहीं है। यदि आप इसे स्पष्ट रूप से सेट करना चाहते हैं, तो आप इसे इस प्रकार परिभाषित कर सकते हैं:

```js
// wdio.conf.js
export const {
    // ...
    runner: 'local',
    // ...
}
```

## ब्राउज़र रनर

[लोकल रनर](https://www.npmjs.com/package/@wdio/local-runner) के विपरीत, [ब्राउज़र रनर](https://www.npmjs.com/package/@wdio/browser-runner) फ्रेमवर्क को ब्राउज़र के भीतर शुरू और निष्पादित करता है। यह आपको कई अन्य टेस्ट फ्रेमवर्क की तरह JSDOM में चलाने के बजाय यूनिट टेस्ट या कंपोनेंट टेस्ट को एक वास्तविक ब्राउज़र में चलाने की अनुमति देता है। टेस्ट बंडल Chrome 90, Edge 90, Firefox 90 और Safari 14.1 या नए संस्करणों में चलता है। [ब्राउज़र समर्थन](/docs/component-testing#browser-support) देखें।

हालाँकि [JSDOM](https://www.npmjs.com/package/jsdom) का व्यापक रूप से टेस्टिंग के लिए उपयोग किया जाता है, अंततः यह एक वास्तविक ब्राउज़र नहीं है और न ही आप इसके साथ मोबाइल एनवायरनमेंट का अनुकरण कर सकते हैं। इस रनर के साथ WebdriverIO आपको अपने टेस्ट को आसानी से ब्राउज़र में चलाने और पेज पर रेंडर किए गए एलिमेंट्स के साथ इंटरैक्ट करने के लिए WebDriver कमांड का उपयोग करने में सक्षम बनाता है।

यहाँ JSDOM बनाम WebdriverIO के ब्राउज़र रनर में टेस्ट चलाने का एक अवलोकन है

| | JSDOM | WebdriverIO ब्राउज़र रनर |
|-|-------|----------------------------|
|1.| वेब मानकों, विशेष रूप से WHATWG DOM और HTML मानकों के पुनः-कार्यान्वयन का उपयोग करके आपके टेस्ट को Node.js के भीतर चलाता है | आपके टेस्ट को एक वास्तविक ब्राउज़र में निष्पादित करता है और कोड को उस एनवायरनमेंट में चलाता है जिसका उपयोग आपके यूज़र्स करते हैं |
|2.| कंपोनेंट्स के साथ इंटरैक्शन का केवल JavaScript के माध्यम से अनुकरण किया जा सकता है | आप WebDriver प्रोटोकॉल के माध्यम से एलिमेंट्स के साथ इंटरैक्ट करने के लिए [WebdriverIO API](api) का उपयोग कर सकते हैं |
|3.| Canvas समर्थन के लिए [अतिरिक्त डिपेंडेंसीज़](https://www.npmjs.com/package/canvas) की आवश्यकता होती है और इसकी [सीमाएँ हैं](https://github.com/Automattic/node-canvas/issues) | आपके पास वास्तविक [Canvas API](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API) तक पहुँच होती है |
|4.| JSDOM में कुछ [चेतावनियाँ](https://github.com/jsdom/jsdom#caveats) और असमर्थित Web APIs हैं | सभी Web APIs समर्थित हैं क्योंकि टेस्ट एक वास्तविक ब्राउज़र में चलते हैं |
|5.| क्रॉस ब्राउज़र त्रुटियों का पता लगाना असंभव है | मोबाइल ब्राउज़र सहित सभी ब्राउज़र्स के लिए समर्थन |
|6.| एलिमेंट की pseudo states के लिए टेस्ट __नहीं__ कर सकता | `:hover` या `:active` जैसी pseudo states के लिए समर्थन |

यह रनर आपके टेस्ट कोड को कंपाइल करने और उसे ब्राउज़र में लोड करने के लिए [Vite](https://vitejs.dev/) का उपयोग करता है। यह निम्नलिखित कंपोनेंट फ्रेमवर्क के लिए प्रीसेट के साथ आता है:

- React
- Preact
- Vue.js
- Svelte
- SolidJS
- Stencil

प्रत्येक टेस्ट फ़ाइल / टेस्ट फ़ाइल ग्रुप एक ही पेज के भीतर चलता है, जिसका अर्थ है कि टेस्ट के बीच आइसोलेशन की गारंटी देने के लिए प्रत्येक टेस्ट के बीच पेज को रीलोड किया जाता है।

### इंस्टॉल करें

ब्राउज़र रनर का उपयोग करने के लिए आप इसे इस प्रकार इंस्टॉल कर सकते हैं:

```sh
npm install --save-dev @wdio/browser-runner
```

### सेटअप

ब्राउज़र रनर का उपयोग करने के लिए, आपको अपनी `wdio.conf.js` फ़ाइल के भीतर एक `runner` प्रॉपर्टी परिभाषित करनी होगी, उदाहरण के लिए:

```js
// wdio.conf.js
export const {
    // ...
    runner: 'browser',
    // ...
}
```

### रनर विकल्प

ब्राउज़र रनर निम्नलिखित कॉन्फ़िगरेशन की अनुमति देता है:

#### `preset`

यदि आप ऊपर उल्लिखित फ्रेमवर्क में से किसी एक का उपयोग करके कंपोनेंट्स का टेस्ट करते हैं, तो आप एक प्रीसेट परिभाषित कर सकते हैं जो यह सुनिश्चित करता है कि सब कुछ बिना किसी अतिरिक्त प्रयास के कॉन्फ़िगर हो जाए। इस विकल्प का उपयोग `viteConfig` के साथ नहीं किया जा सकता।

__प्रकार:__ `vue` | `svelte` | `solid` | `react` | `preact` | `stencil`<br />
__उदाहरण:__

```js title="wdio.conf.js"
export const {
    // ...
    runner: ['browser', {
        preset: 'svelte'
    }],
    // ...
}
```

#### `viteConfig`

अपना स्वयं का [Vite कॉन्फ़िगरेशन](https://vitejs.dev/config/) परिभाषित करें। आप या तो एक कस्टम ऑब्जेक्ट पास कर सकते हैं या यदि आप डेवलपमेंट के लिए Vite.js का उपयोग करते हैं तो एक मौजूदा `vite.conf.ts` फ़ाइल इम्पोर्ट कर सकते हैं। ध्यान दें कि WebdriverIO टेस्ट हार्नेस सेट अप करने के लिए कस्टम Vite कॉन्फ़िगरेशन को बनाए रखता है।

__प्रकार:__ `string` या [`UserConfig`](https://github.com/vitejs/vite/blob/52e64eb43287d241f3fd547c332e16bd9e301e95/packages/vite/src/node/config.ts#L119-L272) या `(env: ConfigEnv) => UserConfig | Promise<UserConfig>`<br />
__उदाहरण:__

```js title="wdio.conf.ts"
import viteConfig from '../vite.config.ts'

export const {
    // ...
    runner: ['browser', { viteConfig }],
    // या बस:
    runner: ['browser', { viteConfig: '../vites.config.ts' }],
    // या यदि आपके vite config में बहुत सारे प्लगइन्स हैं तो एक फ़ंक्शन का उपयोग करें
    // जिन्हें आप केवल तभी resolve करना चाहते हैं जब वैल्यू पढ़ी जाए
    runner: ['browser', {
        viteConfig: () => ({
            // ...
        })
    }],
    // ...
}
```

#### `headless`

यदि `true` पर सेट किया जाता है, तो रनर टेस्ट को headless चलाने के लिए कैपेबिलिटीज़ को अपडेट करेगा। डिफ़ॉल्ट रूप से यह उन CI एनवायरनमेंट में सक्षम होता है जहाँ `CI` एनवायरनमेंट वेरिएबल `'1'` या `'true'` पर सेट होता है।

__प्रकार:__ `boolean`<br />
__डिफ़ॉल्ट:__ `false`, यदि `CI` एनवायरनमेंट वेरिएबल सेट है तो `true` पर सेट होता है

#### `rootDir`

प्रोजेक्ट रूट डायरेक्टरी।

__प्रकार:__ `string`<br />
__डिफ़ॉल्ट:__ `process.cwd()`

#### `coverage`

WebdriverIO [`istanbul`](https://istanbul.js.org/) के माध्यम से टेस्ट कवरेज रिपोर्टिंग का समर्थन करता है। अधिक जानकारी के लिए [कवरेज विकल्प](#coverage-options) देखें।

__प्रकार:__ `object`<br />
__डिफ़ॉल्ट:__ `undefined`

### कवरेज विकल्प

निम्नलिखित विकल्प कवरेज रिपोर्टिंग को कॉन्फ़िगर करने की अनुमति देते हैं।

#### `enabled`

कवरेज संग्रह सक्षम करता है।

__प्रकार:__ `boolean`<br />
__डिफ़ॉल्ट:__ `false`

#### `include`

glob पैटर्न के रूप में कवरेज में शामिल फ़ाइलों की सूची।

__प्रकार:__ `string[]`<br />
__डिफ़ॉल्ट:__ `[**]`

#### `exclude`

glob पैटर्न के रूप में कवरेज से बाहर रखी गई फ़ाइलों की सूची।

__प्रकार:__ `string[]`<br />
__डिफ़ॉल्ट:__

```
[
  'coverage/**',
  'dist/**',
  'packages/*/test{,s}/**',
  '**/*.d.ts',
  'cypress/**',
  'test{,s}/**',
  'test{,-*}.{js,cjs,mjs,ts,tsx,jsx}',
  '**/*{.,-}test.{js,cjs,mjs,ts,tsx,jsx}',
  '**/*{.,-}spec.{js,cjs,mjs,ts,tsx,jsx}',
  '**/__tests__/**',
  '**/{karma,rollup,webpack,vite,vitest,jest,ava,babel,nyc,cypress,tsup,build}.config.*',
  '**/.{eslint,mocha,prettier}rc.{js,cjs,yml}',
]
```

#### `extension`

फ़ाइल एक्सटेंशन की सूची जिन्हें रिपोर्ट में शामिल किया जाना चाहिए।

__प्रकार:__ `string | string[]`<br />
__डिफ़ॉल्ट:__ `['.js', '.cjs', '.mjs', '.ts', '.mts', '.cts', '.tsx', '.jsx', '.vue', '.svelte']`

#### `reportsDirectory`

वह डायरेक्टरी जिसमें कवरेज रिपोर्ट लिखी जाएगी।

__प्रकार:__ `string`<br />
__डिफ़ॉल्ट:__ `./coverage`

#### `reporter`

उपयोग किए जाने वाले कवरेज रिपोर्टर्स। सभी रिपोर्टर्स की विस्तृत सूची के लिए [istanbul डॉक्यूमेंटेशन](https://istanbul.js.org/docs/advanced/alternative-reporters/) देखें।

__प्रकार:__ `string[]`<br />
__डिफ़ॉल्ट:__ `['text', 'html', 'clover', 'json-summary']`

#### `perFile`

प्रति फ़ाइल थ्रेशोल्ड की जाँच करें। वास्तविक थ्रेशोल्ड के लिए `lines`, `functions`, `branches` और `statements` देखें।

__प्रकार:__ `boolean`<br />
__डिफ़ॉल्ट:__ `false`

#### `clean`

टेस्ट चलाने से पहले कवरेज परिणामों को साफ़ करें।

__प्रकार:__ `boolean`<br />
__डिफ़ॉल्ट:__ `true`

#### `lines`

लाइनों के लिए थ्रेशोल्ड।

__प्रकार:__ `number`<br />
__डिफ़ॉल्ट:__ `undefined`

#### `functions`

फ़ंक्शन्स के लिए थ्रेशोल्ड।

__प्रकार:__ `number`<br />
__डिफ़ॉल्ट:__ `undefined`

#### `branches`

ब्रांचेज़ के लिए थ्रेशोल्ड।

__प्रकार:__ `number`<br />
__डिफ़ॉल्ट:__ `undefined`

#### `statements`

स्टेटमेंट्स के लिए थ्रेशोल्ड।

__प्रकार:__ `number`<br />
__डिफ़ॉल्ट:__ `undefined`

### सीमाएँ

WebdriverIO ब्राउज़र रनर का उपयोग करते समय, यह ध्यान रखना महत्वपूर्ण है कि `alert` या `confirm` जैसे थ्रेड ब्लॉक करने वाले डायलॉग्स का नेटिव रूप से उपयोग नहीं किया जा सकता। ऐसा इसलिए है क्योंकि वे वेब पेज को ब्लॉक कर देते हैं, जिसका अर्थ है कि WebdriverIO पेज के साथ संचार जारी नहीं रख सकता, जिससे निष्पादन रुक (hang) जाता है।

ऐसी स्थितियों में, WebdriverIO इन APIs के लिए डिफ़ॉल्ट रिटर्न वैल्यू के साथ डिफ़ॉल्ट मॉक प्रदान करता है। यह सुनिश्चित करता है कि यदि यूज़र गलती से सिंक्रोनस पॉपअप वेब APIs का उपयोग करता है, तो निष्पादन नहीं रुकेगा। हालाँकि, बेहतर अनुभव के लिए यूज़र को इन वेब APIs को मॉक करने की अभी भी सलाह दी जाती है। [मॉकिंग](/docs/component-testing/mocking) में और पढ़ें।

### उदाहरण

[कंपोनेंट टेस्टिंग](https://webdriver.io/docs/component-testing) से संबंधित डॉक्यूमेंटेशन को अवश्य देखें और इन तथा विभिन्न अन्य फ्रेमवर्क का उपयोग करने वाले उदाहरणों के लिए [उदाहरण रिपॉजिटरी](https://github.com/webdriverio/component-testing-examples) पर एक नज़र डालें।
