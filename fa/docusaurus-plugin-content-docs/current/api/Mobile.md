# مقدمه‌ای بر دستورات سفارشی و بهبودیافته موبایل در WebdriverIO

تست اپلیکیشن‌های موبایل و وب‌اپلیکیشن‌های موبایل چالش‌های خاص خود را دارد، به‌ویژه هنگام مواجهه با تفاوت‌های مختص هر پلتفرم بین Android و iOS. اگرچه Appium انعطاف‌پذیری لازم برای مدیریت این تفاوت‌ها را فراهم می‌کند، اما اغلب نیاز دارد که عمیقاً در مستندات ([Android](https://appium.github.io/appium-uiautomator2-driver/latest/reference/execute-methods/#gestures)، [iOS](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/)) و دستورات پیچیده و وابسته به پلتفرم غوطه‌ور شوید. این موضوع می‌تواند نوشتن اسکریپت‌های تست را زمان‌برتر، مستعد خطا و نگهداری آن‌ها را دشوارتر کند.

برای ساده‌سازی این فرایند، WebdriverIO **دستورات سفارشی و بهبودیافته موبایل** را معرفی می‌کند که به‌طور خاص برای تست وب موبایل و اپلیکیشن‌های بومی (native) طراحی شده‌اند. این دستورات پیچیدگی‌های APIهای زیربنایی Appium را پنهان می‌کنند و به شما امکان می‌دهند اسکریپت‌های تست مختصر، قابل‌فهم و مستقل از پلتفرم بنویسید. با تمرکز بر سهولت استفاده، هدف ما کاهش بار اضافی در هنگام توسعه اسکریپت‌های Appium و توانمندسازی شما برای خودکارسازی آسان اپلیکیشن‌های موبایل است.

## چرا دستورات سفارشی موبایل؟

### 1. **ساده‌سازی APIهای پیچیده**
برخی از دستورات Appium، مانند حرکات لمسی (gestures) یا تعامل با المان‌ها، دارای نحو طولانی و پیچیده‌ای هستند. برای مثال، اجرای یک عمل فشار طولانی (long press) با API بومی Appium نیازمند ساخت دستی یک زنجیره `action` است:

```ts
const element = $('~Contacts')

await browser
    .action( 'pointer', { parameters: { pointerType: 'touch' } })
    .move({ origin: element })
    .down()
    .pause(1500)
    .up()
    .perform()
```

با دستورات سفارشی WebdriverIO، همین عمل را می‌توان تنها با یک خط کد گویا انجام داد:

```ts
await $('~Contacts').longPress();
```

این کار کدهای تکراری (boilerplate) را به‌شدت کاهش می‌دهد و اسکریپت‌های شما را تمیزتر و قابل‌فهم‌تر می‌کند.

### 2. **انتزاع چندپلتفرمی**
اپلیکیشن‌های موبایل اغلب نیازمند مدیریت مختص هر پلتفرم هستند. برای مثال، اسکرول کردن در اپلیکیشن‌های بومی بین [Android](https://appium.github.io/appium-uiautomator2-driver/latest/reference/execute-methods/#mobile-scrollgesture) و [iOS](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/#mobile-scroll) تفاوت قابل‌توجهی دارد. WebdriverIO با ارائه دستورات یکپارچه‌ای مانند `scrollIntoView()` که بدون توجه به پیاده‌سازی زیربنایی، به‌طور یکپارچه در همه پلتفرم‌ها کار می‌کنند، این شکاف را پر می‌کند.

```ts
await $('~element').scrollIntoView();
```

این انتزاع تضمین می‌کند که تست‌های شما قابل‌انتقال باشند و برای در نظر گرفتن تفاوت‌های سیستم‌عامل، نیازی به انشعاب‌های مداوم یا منطق شرطی نداشته باشند.

### 3. **افزایش بهره‌وری**
با کاهش نیاز به درک و پیاده‌سازی دستورات سطح پایین Appium، دستورات موبایل WebdriverIO به شما امکان می‌دهند به‌جای درگیر شدن با جزئیات مختص هر پلتفرم، بر تست عملکرد اپلیکیشن خود تمرکز کنید. این موضوع به‌ویژه برای تیم‌هایی که تجربه محدودی در خودکارسازی موبایل دارند یا به دنبال تسریع چرخه توسعه خود هستند، سودمند است.

### 4. **یکپارچگی و قابلیت نگهداری**
دستورات سفارشی به اسکریپت‌های تست شما یکنواختی می‌بخشند. به‌جای داشتن پیاده‌سازی‌های متفاوت برای اعمال مشابه، تیم شما می‌تواند به دستورات استاندارد و قابل‌استفاده مجدد تکیه کند. این کار نه‌تنها نگهداری کدبیس را آسان‌تر می‌کند، بلکه موانع ورود اعضای جدید تیم را نیز کاهش می‌دهد.

## چرا برخی دستورات موبایل را بهبود دهیم؟

### 1. افزودن انعطاف‌پذیری
برخی از دستورات موبایل بهبود یافته‌اند تا گزینه‌ها و پارامترهای اضافی را ارائه دهند که در APIهای پیش‌فرض Appium موجود نیستند. برای مثال، WebdriverIO منطق تلاش مجدد (retry)، مهلت‌های زمانی (timeout) و قابلیت فیلتر کردن webviewها بر اساس معیارهای خاص را اضافه می‌کند و کنترل بیشتری بر سناریوهای پیچیده فراهم می‌سازد.

```ts
// Example: Customizing retry intervals and timeouts for webview detection
await driver.getContexts({
  returnDetailedContexts: true,
  androidWebviewConnectionRetryTime: 1000, // Retry every 1 second
  androidWebviewConnectTimeout: 10000,    // Timeout after 10 seconds
});
```

این گزینه‌ها به تطبیق اسکریپت‌های خودکارسازی با رفتار پویای اپلیکیشن، بدون نیاز به کدهای تکراری اضافی، کمک می‌کنند.

### 2. بهبود کاربردپذیری
دستورات بهبودیافته، پیچیدگی‌ها و الگوهای تکراری موجود در APIهای بومی را پنهان می‌کنند. آن‌ها به شما امکان می‌دهند با خطوط کد کمتر، اعمال بیشتری انجام دهید، که منحنی یادگیری را برای کاربران جدید کاهش داده و خواندن و نگهداری اسکریپت‌ها را آسان‌تر می‌کند.

```ts
// Example: Enhanced command for switching context by title
await driver.switchContext({
  title: 'My Webview Title',
});
```

در مقایسه با متدهای پیش‌فرض Appium، دستورات بهبودیافته نیاز به مراحل اضافی مانند بازیابی دستی contextهای موجود و فیلتر کردن آن‌ها را از بین می‌برند.

### 3. استانداردسازی رفتار
WebdriverIO تضمین می‌کند که دستورات بهبودیافته در پلتفرم‌هایی مانند Android و iOS رفتار یکسانی داشته باشند. این انتزاع چندپلتفرمی نیاز به منطق انشعاب شرطی بر اساس سیستم‌عامل را به حداقل می‌رساند و منجر به اسکریپت‌های تست با قابلیت نگهداری بیشتر می‌شود.

```ts
// Example: Unified scroll command for both platforms
await $('~element').scrollIntoView();
```

این استانداردسازی کدبیس‌ها را ساده می‌کند، به‌ویژه برای تیم‌هایی که تست‌ها را روی چندین پلتفرم خودکارسازی می‌کنند.

### 4. افزایش قابلیت اطمینان
دستورات بهبودیافته با به‌کارگیری مکانیزم‌های تلاش مجدد، پیش‌فرض‌های هوشمند و پیام‌های خطای دقیق، احتمال بروز تست‌های ناپایدار (flaky) را کاهش می‌دهند. این بهبودها تضمین می‌کنند که تست‌های شما در برابر مشکلاتی مانند تأخیر در راه‌اندازی webview یا وضعیت‌های گذرای اپلیکیشن مقاوم باشند.

```ts
// Example: Enhanced webview switching with robust matching logic
await driver.switchContext({
  url: /.*my-app\/dashboard/,
  androidWebviewConnectionRetryTime: 500,
  androidWebviewConnectTimeout: 7000,
});
```

این کار اجرای تست را قابل‌پیش‌بینی‌تر کرده و احتمال شکست‌های ناشی از عوامل محیطی را کاهش می‌دهد.

### 5. ارتقای قابلیت‌های اشکال‌زدایی
دستورات بهبودیافته اغلب فراداده (metadata) غنی‌تری بازمی‌گردانند که اشکال‌زدایی سناریوهای پیچیده، به‌ویژه در اپلیکیشن‌های هیبریدی، را آسان‌تر می‌کند. برای مثال، دستوراتی مانند getContext و getContexts می‌توانند اطلاعات دقیقی درباره webviewها، از جمله عنوان، url و وضعیت نمایش، بازگردانند.

```ts
// Example: Retrieving detailed metadata for debugging
const contexts = await driver.getContexts({ returnDetailedContexts: true });
console.log(contexts);
```

این فراداده به شناسایی و رفع سریع‌تر مشکلات کمک کرده و تجربه کلی اشکال‌زدایی را بهبود می‌بخشد.


WebdriverIO با بهبود دستورات موبایل، نه‌تنها خودکارسازی را آسان‌تر می‌کند، بلکه با مأموریت خود مبنی بر ارائه ابزارهایی قدرتمند، قابل‌اعتماد و با کاربری آسان به توسعه‌دهندگان نیز همسو است.

## اپلیکیشن‌های هیبریدی

اپلیکیشن‌های هیبریدی محتوای وب را با قابلیت‌های بومی ترکیب می‌کنند و در طول خودکارسازی نیازمند مدیریت ویژه‌ای هستند. این اپلیکیشن‌ها از webviewها برای نمایش محتوای وب درون یک اپلیکیشن بومی استفاده می‌کنند. WebdriverIO متدهای بهبودیافته‌ای را برای کار مؤثر با اپلیکیشن‌های هیبریدی فراهم می‌کند.

### درک Webviewها
webview یک کامپوننت شبیه مرورگر است که درون یک اپلیکیشن بومی تعبیه شده است:

- **Android:** webviewها بر پایه Chrome/System Webview هستند و ممکن است شامل چندین صفحه (مشابه تب‌های مرورگر) باشند. این webviewها برای خودکارسازی تعاملات به ChromeDriver نیاز دارند. Appium می‌تواند نسخه موردنیاز ChromeDriver را بر اساس نسخه System WebView یا Chrome نصب‌شده روی دستگاه به‌طور خودکار تشخیص دهد و در صورت عدم وجود، آن را به‌طور خودکار دانلود کند. این رویکرد سازگاری یکپارچه را تضمین کرده و تنظیمات دستی را به حداقل می‌رساند. برای آشنایی با نحوه دانلود خودکار نسخه صحیح ChromeDriver توسط Appium، به [مستندات Appium UIAutomator2](https://appium.github.io/appium-uiautomator2-driver/latest/guides/hybrid/#automatic-discovery) مراجعه کنید.
- **iOS:** webviewها توسط Safari (WebKit) پشتیبانی می‌شوند و با شناسه‌های عمومی مانند `WEBVIEW_{id}` شناسایی می‌شوند.

### چالش‌های اپلیکیشن‌های هیبریدی
1. شناسایی webview صحیح از میان چندین گزینه.
2. بازیابی فراداده‌های اضافی مانند عنوان، URL یا نام بسته (package name) برای درک بهتر context.
3. مدیریت تفاوت‌های مختص هر پلتفرم بین Android و iOS.
4. جابه‌جایی قابل‌اعتماد به context صحیح در یک اپلیکیشن هیبریدی.

### دستورات کلیدی برای اپلیکیشن‌های هیبریدی

#### 1. `getContext`
context فعلی نشست (session) را بازیابی می‌کند. به‌طور پیش‌فرض، مانند متد getContext در Appium رفتار می‌کند، اما در صورت فعال بودن `returnDetailedContext` می‌تواند اطلاعات دقیق context را ارائه دهد. برای اطلاعات بیشتر به [`getContext`](/docs/api/mobile/getContext) مراجعه کنید.

#### 2. `getContexts`
فهرست دقیقی از contextهای موجود را بازمی‌گرداند که نسخه بهبودیافته متد contexts در Appium است. این کار شناسایی webview صحیح برای تعامل را بدون نیاز به فراخوانی دستورات اضافی برای تعیین عنوان، url یا `bundleId|packageName` فعال، آسان‌تر می‌کند. برای اطلاعات بیشتر به [`getContexts`](/docs/api/mobile/getContexts) مراجعه کنید.

#### 3. `switchContext`
بر اساس نام، عنوان یا url به یک webview خاص جابه‌جا می‌شود. انعطاف‌پذیری بیشتری مانند استفاده از عبارات منظم (regular expressions) برای تطبیق فراهم می‌کند. برای اطلاعات بیشتر به [`switchContext`](/docs/api/mobile/switchContext) مراجعه کنید.

### ویژگی‌های کلیدی برای اپلیکیشن‌های هیبریدی
1. فراداده دقیق: بازیابی جزئیات جامع برای اشکال‌زدایی و جابه‌جایی قابل‌اعتماد بین contextها.
2. یکپارچگی چندپلتفرمی: رفتار یکسان برای Android و iOS، با مدیریت یکپارچه ویژگی‌های خاص هر پلتفرم.
3. منطق تلاش مجدد سفارشی (Android): تنظیم فواصل تلاش مجدد و مهلت‌های زمانی برای تشخیص webview.


:::info نکات و محدودیت‌ها
- Android فراداده‌های اضافی مانند `packageName` و `webviewPageId` را ارائه می‌دهد، در حالی که iOS بر `bundleId` تمرکز دارد.
- منطق تلاش مجدد برای Android قابل سفارشی‌سازی است اما برای iOS کاربرد ندارد.
- موارد متعددی وجود دارد که iOS نمی‌تواند Webview را پیدا کند. Appium قابلیت‌های (capabilities) اضافی مختلفی را برای `appium-xcuitest-driver` جهت یافتن Webview فراهم می‌کند. اگر فکر می‌کنید Webview پیدا نمی‌شود، می‌توانید یکی از قابلیت‌های زیر را تنظیم کنید:
    - `appium:includeSafariInWebviews`: contextهای وب Safari را به فهرست contextهای موجود در طول تست اپلیکیشن native/webview اضافه می‌کند. این مورد زمانی مفید است که تست، Safari را باز می‌کند و نیاز دارد با آن تعامل داشته باشد. مقدار پیش‌فرض `false` است.
    - `appium:webviewConnectRetries`: حداکثر تعداد تلاش‌های مجدد پیش از توقف تشخیص صفحات web view. تأخیر بین هر تلاش مجدد 500ms است و مقدار پیش‌فرض `10` تلاش مجدد است.
    - `appium:webviewConnectTimeout`: حداکثر مدت‌زمان به میلی‌ثانیه برای انتظار تشخیص یک صفحه web view. مقدار پیش‌فرض `5000` میلی‌ثانیه است.

برای مثال‌ها و جزئیات پیشرفته، به مستندات API موبایل WebdriverIO مراجعه کنید.
:::
