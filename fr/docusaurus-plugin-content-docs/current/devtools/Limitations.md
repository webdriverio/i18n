Ce que le [mode trace](/docs/devtools/wdio/trace-mode) ignore délibérément, ainsi que les lacunes connues selon les adaptateurs.

## Ce que le mode trace ignore

- **Fenêtre de l'interface DevTools** — aucune instance de Chrome ne s'ouvre pour le tableau de bord.
- **Liaison du port du backend** : les adaptateurs JavaScript ne réservent aucun port localhost. L'adaptateur Python démarre toujours le backend (ou s'y attache), car c'est le backend qui construit l'archive, mais il n'ouvre aucune fenêtre.
- **`screencast.enabled`** — l'enregistrement `.webm` continu du mode live est ignoré en mode trace (un avertissement est journalisé). Le mode trace enregistre à la place une [`filmstrip`](/docs/devtools/wdio/trace-mode#dense-filmstrip--filmstrip) dense dans l'archive **par défaut** (définissez `filmstrip: false` pour obtenir une image par action), ainsi que des segments [`video`](/docs/devtools/wdio/trace-mode#per-test-screenshot--video--screenshot--video) par test lorsqu'ils sont activés. Les champs de **réglage** du screencast (`quality`, `maxWidth`, `pollIntervalMs`, …) s'appliquent toujours à l'enregistreur utilisé.
- **Export `wdio-trace-<sessionId>.json`** — entièrement supprimé. L'ancien JSON monolithique qu'écrivait le mode live de WDIO a disparu ; le mode live diffuse désormais vers le tableau de bord sans rien écrire sur le disque, et le `trace.zip` est l'unique artefact de trace.

## Limitations connues

- **Nightwatch BDD `describe/it`** — `traceGranularity: 'test'` se réduit à un **unique segment à l'échelle de la session** : Nightwatch exécute les `it` individuels en interne sans hook par test visible par le plugin, si bien que le segment est associé au premier test. La capture des métadonnées (état par cas de test dans le manifeste) n'est pas affectée, mais l'association des traces/captures d'écran/vidéos par `it` et la rétention tenant compte des relances sont ramenées à l'échelle de la session pour cette interface. Les interfaces **exports-object** et **Cucumber** de Nightwatch exposent des hooks par scénario/par test et bénéficient d'un véritable découpage par test. (WebdriverIO mocha/cucumber et Selenium mocha ne sont pas affectés.)
- **Rétention tenant compte des relances dans Nightwatch** — seul `retain-on-failure` fonctionne ; les autres politiques tenant compte des relances sont dégradées, car Nightwatch réexécute un cas de test en interne avec `--retries` sans redéclencher les hooks par test. Voir [Rétention](/docs/devtools/wdio/trace-mode#retention--tracepolicy).
- **Pièces jointes Allure dans Nightwatch** — les `screenshot`/`video` par test sont uniquement produits (fichiers + manifeste), et non joints en ligne ; voir [Intégration Allure](/docs/devtools/allure).
- **WebdriverIO nécessite WebDriver BiDi** pour la capture de page (Chrome 114+, Firefox 130+ ; activé automatiquement). Les sessions Appium l'ignorent ; définissez-y `'wdio:enforceWebDriverClassic': true`.
- **En mode live, Safari doit rester la fenêtre au premier plan** : Safari ne transmet les clics et frappes synthétisés qu'à sa fenêtre au premier plan et signale un succès dans tous les cas, de sorte que toute saisie émise alors que le tableau de bord ou une autre fenêtre est au premier plan n'atteint rien. L'adaptateur Selenium (Node.js) ouvre son tableau de bord derrière Safari et ramène la fenêtre de la session au premier plan avant chaque saisie ; le service WebdriverIO, Nightwatch et Python ramènent Safari au premier plan une seule fois après le démarrage de la session (macOS, Safari local uniquement). Ne cliquez pas dans d'autres fenêtres, y compris le tableau de bord, pendant une exécution live sous Safari. Le mode trace n'ouvre aucune fenêtre et n'est pas concerné.
- **Réseau sans BiDi** : sur les sessions Safari et Appium, l'onglet Network provient du patch de `fetch` / `XMLHttpRequest` de la page elle-même et du tampon Resource Timing ; les chargements que la page n'a pas effectués via `fetch` / XHR ne comportent donc ni en-têtes ni corps, et sur Safari aucun statut. Une session d'application native ne capture le réseau que via le plugin appium-interceptor (`appium:intercept: true`, Android) ; voir [Réseau des applications natives](/docs/devtools/mobile#native-app-network). Voir [Journaux réseau](/docs/devtools/wdio/network-logs#without-webdriver-bidi).
- **Applications hybrides** : seul WebdriverIO suit une application hybride dans sa webview, et les actions dans la webview d'une application hybride ne comportent ni données d'élément par action, ni arbre A11y, ni capture d'écran de stabilisation. Voir [Tests mobiles](/docs/devtools/mobile).
- **Aucune expurgation** : une trace enregistre tout ce que l'exécution a affiché ou saisi : mutations du DOM, arguments de `fill`, transcription et code source du test. Seules les valeurs des champs de mot de passe sont masquées dans l'instantané des éléments, et le texte saisi apparaît toujours dans le flux de mutations. Considérez une archive de trace comme aussi sensible que l'exécution qui l'a produite.
- **Vidéo/filmstrip hors Chrome** — sur les navigateurs sans mécanisme de push CDP, l'enregistreur interroge `takeScreenshot`, ce qui ajoute des allers-retours WebDriver et (avec Allure) inonde le journal des étapes ; combinez-le avec les options de mise en sourdine des étapes du reporter.
