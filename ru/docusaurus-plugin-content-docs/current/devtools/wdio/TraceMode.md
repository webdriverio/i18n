Захват в headless-режиме — окно интерфейса DevTools не открывается. В конце сессии адаптер записывает артефакты трассировки в папку `test-results/` рядом с каталогом ваших спецификаций / конфигурации. Для гранулярности `session` / `spec` это `trace-<sessionId>.zip` (или каталог `trace-<sessionId>/`); для гранулярности `test` каждый тест получает собственную подпапку (см. [Гранулярность трассировки](#trace-granularity--tracegranularity)). Артефакт переносим и содержит всё необходимое для офлайн-воспроизведения, сравнения запусков AI-агентом или любого потребителя, которому файл удобнее живого интерфейса.

Режим трассировки **взаимоисключающий с live-режимом**. Выберите один на сессию: людям, отлаживающим интерактивно, нужен live; агентам, сравнивающим запуски, или CI-ботам, собирающим артефакты, нужна трассировка.

## Включение

```ts
// wdio.conf.ts
services: [
  [
    'devtools',
    {
      mode: 'trace',
      traceFormat: 'zip' // необязательно; 'zip' (по умолчанию) | 'ndjson-directory'
    }
  ]
]
```

Полный готовый к копированию эталонный конфиг находится в [`examples/wdio/wdio.trace.conf.ts`](https://github.com/webdriverio/devtools/blob/main/examples/wdio/wdio.trace.conf.ts).

Selenium и Nightwatch используют тот же конвейер трассировки — синтаксис включения для конкретного фреймворка смотрите на страницах их адаптеров: [Selenium](/docs/devtools/selenium#trace-mode) · [Nightwatch](/docs/devtools/nightwatch#trace-mode).

## Что внутри артефакта

| Файл | Содержимое |
|---|---|
| `trace.trace` | NDJSON-события `context-options` + `before` / `after` для действий; одна строка на запись |
| `trace.network` | Сетевые записи в стиле HAR, по одной на строку |
| `transcript.md` | Читаемая человеком/LLM сводка в Markdown с таймингами, селекторами, аннотациями значений |
| `resources/page@<id>-<ts>.jpeg` | Скриншот, сделанный при каждом пользовательском действии |
| `resources/page@<id>-<ts>-elements.json` | Плоский список интерактивных элементов на момент действия |
| `resources/page@<id>-<ts>-snapshot.txt` | Снимок дерева доступности с отступами по глубине (удобен для AI) |

### Что считается «действием»

Команды фильтруются через список разрешённых, прежде чем попасть в трассировку. Примеры того, что попадает в трассировку:

- `url` / `get` → `Page.navigate`
- `click` → `Element.click`
- `setValue` / `sendKeys` → `Element.fill`
- `submit`, `clear`, `selectByVisibleText`, …

Внутренние команды, такие как `findElement`, `waitUntil`, `executeScript`, намеренно исключены — они не отражают намерения пользователя и засоряли бы временную шкалу. Полный список разрешённых команд находится в [`@wdio/devtools-core/action-mapping.ts`](https://github.com/webdriverio/devtools/blob/main/packages/core/src/action-mapping.ts).

## Формат вывода — `traceFormat`

```ts
{
  mode: 'trace',
  traceFormat: 'zip' | 'ndjson-directory'  // по умолчанию: 'zip'
}
```

- **`zip`** (по умолчанию) — единый архив в `test-results/trace-<sessionId>.zip`.
- **`ndjson-directory`** — те же файлы, распакованные в `test-results/trace-<sessionId>/`. На один шаг распаковки меньше для скриптовых или агентных потребителей, которые хотят напрямую выполнять grep / потоково читать NDJSON.

Оба формата открываются в фирменном [плеере `show-trace`](/docs/devtools/trace-player) и в других совместимых просмотрщиках трассировок.

## Гранулярность трассировки — `traceGranularity`

Сколько артефактов трассировки создаёт запуск:

```ts
{
  mode: 'trace',
  traceGranularity: 'session' | 'spec' | 'test' // по умолчанию: 'session'
}
```

| Значение | Результат |
|---|---|
| `session` (по умолчанию) | Одна трассировка на воркер/сессию — `test-results/trace-<sessionId>.zip`. |
| `spec` | Одна трассировка на файл спецификации. Меньше по размеру, проще в навигации. |
| `test` | Одна трассировка **на тест**, каждая в своей папке: `test-results/<spec>-<title>-<browser>[-retry<N>]/trace.zip`. |

Для гранулярности `test` имя папки формируется из базового имени спецификации, slug-версии названия теста, браузера и суффикса `-retry<N>` для повторных попыток — например, `test-results/login_e2e-logs-in-chrome/trace.zip`, а первый повтор — в `test-results/login_e2e-logs-in-chrome-retry1/trace.zip`. Трассировки по тестам наиболее удобны для навигации и лучше всего сочетаются с политикой хранения, чтобы записывались только нужные вам трассировки.

## Хранение — `tracePolicy`

По умолчанию сохраняется каждая трассировка (`'on'`). Чтобы сохранять только интересные — идеально в сочетании с `traceGranularity: 'test'`:

```ts
{
  mode: 'trace',
  traceGranularity: 'test',
  tracePolicy: 'retain-on-failure' // по умолчанию: 'on'
}
```

| Политика | Сохраняет трассировку, когда… |
|---|---|
| `'on'` (по умолчанию) | Всегда — записывается каждая трассировка. |
| `'retain-on-failure'` | **Последняя** попытка теста завершилась неудачей. Последовательность «провал, затем успех» заканчивается статусом `passed`, поэтому трассировка *не* сохраняется — вы не храните лишнего для нестабильного теста, который в итоге прошёл. |
| `'retain-on-first-failure'` | **Попытка 0** завершилась неудачей, независимо от того, прошёл ли последующий повтор. |
| `'on-first-retry'` | Тест был повторён хотя бы один раз (существует попытка 1). |
| `'on-all-retries'` | Существует любая повторная попытка (попытка ≥ 1). |
| `'retain-on-failure-and-retries'` | Последняя попытка провалилась **или** тест был повторён. |

Решение о несохраняемом фрагменте принимается заранее, и он никогда не записывается на диск. Политики, учитывающие повторы, опираются на **журнал исходов** по попыткам, который адаптер ведёт для каждого стабильного между повторами идентификатора теста, поэтому `retain-on-failure` и `retain-on-first-failure` оценивают правильную попытку. Если раннер не предоставляет информацию о повторах по попыткам, каждая политика, кроме `retain-on-failure`, деградирует до `retain-on-failure`; запуск без зафиксированных исходов (например, обычный standalone-скрипт) отказывает в **открытую** сторону и сохраняет трассировку, вместо того чтобы рисковать потерять нужную.

> Хранение с учётом повторов проверено end-to-end для **WebdriverIO** (mocha / cucumber) и **Selenium** (mocha). Для **Nightwatch** `retain-on-failure` работает, но остальные политики с учётом повторов деградируют до неё, потому что `--retries` в Nightwatch перезапускает testcase внутренне, не вызывая повторно хуки уровня теста. Межпроцессный `specFileRetries` в WDIO также выходит за рамки журнала (который ведётся на уровне воркера). Подробности смотрите на [странице адаптера Nightwatch](/docs/devtools/nightwatch#trace-mode).

## Плотная раскадровка — `filmstrip`

**По умолчанию** трассировка записывает **плотный, непрерывный** скринкаст, чтобы плеер обеспечивал плавное воспроизведение при перемотке, а не перескакивал от кадра к кадру. Плотные кадры располагаются рядом с кадрами действий (которые содержат снимки DOM). Установите `filmstrip: false`, чтобы записывать только один кадр на действие — трассировка меньшего размера без непрерывной записи:

```ts
{
  mode: 'trace',
  filmstrip: false // отключение — один кадр на действие (по умолчанию true)
}
```

- Плотные кадры добавляются **рядом** с кадрами действий (которые содержат снимки DOM), поэтому данные DOM не теряются — при наличии плотных кадров они заменяют разреженную раскадровку по действиям при перемотке.
- При экспорте кадры прореживаются (интервал ≥100 мс) и адресуются по содержимому, поэтому одинаковые кадры (статичное ожидание) схлопываются в один ресурс. Буфер живой сессии ограничен `screencast.maxBufferFrames` (по умолчанию 2000).
- Запись использует рекордер скринкаста — CDP push в Chrome/Chromium, опрос скриншотами в остальных браузерах. В браузерах, отличных от Chrome, опрос отправляет множество команд `takeScreenshot`; используйте вместе с опцией скрытия шагов вашего репортера (см. [Интеграция с Allure](/docs/devtools/allure)).

`filmstrip` доступен во всех трёх адаптерах (WebdriverIO / Selenium / Nightwatch).

## Скриншот и видео для каждого теста — `screenshot` / `video`

При `traceGranularity: 'test'` каждый тест также может создавать отдельный скриншот и/или фрагмент видео, повторяя привычную эргономику «скриншот/видео при падении»:

```ts
{
  mode: 'trace',
  traceGranularity: 'test',
  screenshot: 'only-on-failure', // 'off' (по умолчанию) | 'on' | 'only-on-failure'
  video: 'retain-on-failure'     // 'off' (по умолчанию) | любое значение tracePolicy
}
```

| Опция | Значения | Поведение |
|---|---|---|
| `screenshot` | `'off'` (по умолчанию) · `'on'` · `'only-on-failure'` | `'on'` делает снимок после каждого теста; `'only-on-failure'` — только после упавшего теста. PNG. |
| `video` | `'off'` (по умолчанию) · любое значение `tracePolicy` | Непрерывно записывает скринкаст и сохраняет фрагмент каждого теста по той же семантике хранения, что и `tracePolicy`. WebM. Установка значения, отличного от `off`, сама запускает рекордер — дополнительно включать `filmstrip` или `screencast.enabled` не нужно. |

Обе опции работают только в режиме трассировки + `traceGranularity: 'test'` (уровень теста, к которому они привязываются). При более грубой гранулярности они ничего не делают.

- **WebdriverIO** — `screenshot` / `video` являются опциями сервиса; прикрепляются inline к Allure, если присутствует `@wdio/allure-reporter`.
- **Selenium** — те же опции в его `DevToolsOptions`; прикрепляются inline к Allure через `allure-js-commons`, когда активен адаптер раннера Allure.
- **Nightwatch** — **только создание**: файлы записываются в каталог вывода трассировки (и перечисляются в манифесте), но не прикрепляются inline к Allure — у Nightwatch нет API для прикрепления к Allure в реальном времени. См. [Ограничения режима трассировки](/docs/devtools/limitations).

> `screencast.enabled` — это отдельная непрерывная запись `.webm` в **live-режиме**, в режиме трассировки она игнорируется. В режиме трассировки используйте `filmstrip` (плотные кадры в трассировке) или `video` для каждого теста; поля настройки скринкаста (`quality`, `maxWidth`, `pollIntervalMs`, …) по-прежнему применяются к тому рекордеру, который работает.

## Манифест артефактов — `emitArtifactsManifest`

Записывает `devtools-artifacts-<sessionId>.json` рядом с трассировкой — универсальный индекс, который репортеры и CI используют для обнаружения созданных артефактов (каждой трассировки / скриншота / видео, а также состояния каждого теста):

```ts
{
  mode: 'trace',
  emitArtifactsManifest: true // по умолчанию: выкл.; включается автоматически при обнаружении Allure
}
```

- **Выключен по умолчанию.** Он **включается автоматически**, когда обнаружен репортер Allure — `@wdio/allure-reporter` в конфиге WebdriverIO или активная среда выполнения `allure-js-commons` в Selenium.
- **В Nightwatch включается вручную**: у него нет сигнала Allure в реальном времени для автоопределения (`nightwatch-allure` работает постфактум), поэтому он никогда не включается автоматически — задайте опцию явно, если вам нужен манифест.

## Проверки — `captureAssertions`

Проверки отображаются как полноценные строки действий в трассировке (включено по умолчанию; установите `captureAssertions: false`, чтобы отключить):

- **`node:assert`** — фиксируются во всех трёх адаптерах как строки `assert.<method>`.
- **WebdriverIO `expect`** — успешные *и* неуспешные матчеры `expect(...)` (`expect($el).toHaveText(...)`, `toBeExisting()`, …) отображаются как строки `expect.<matcher>` с ожидаемым значением, местоположением элемента в исходном коде и снимком; внутренние команды опроса матчера подавляются, чтобы отображалась только проверка.
- **Nightwatch `browser.assert.*` / `browser.verify.*`** — нативные проверки отображаются как строки `assert.<m>` / `verify.<m>`.

Успешные проверки отображаются зелёным; неуспешные — красным с сообщением об ошибке.

## Мобильное тестирование

Режим трассировки определяет мобильные сессии по `platformName: 'android' | 'ios'` (без учёта регистра) и подстраивается:

- **Мобильный веб** (Chrome на Android, Safari на iOS): тот же конвейер снимков на основе DOM, что и на десктопе.
- **Нативные мобильные приложения**: внедряемые в страницу DOM-скрипты отключаются; для получения XML-дерева Appium используется `getPageSource()`, которое передаётся в сериализатор снимков.

В `context-options` трассировки записывается `title: 'android — <deviceName>'` / `'ios — <deviceName>'`, чтобы просмотрщик правильно подписывал кадры. Эталонный конфиг WDIO для Android Chrome через Appium находится в [`examples/wdio/wdio.mobile.conf.ts`](https://github.com/webdriverio/devtools/blob/main/examples/wdio/wdio.mobile.conf.ts).

## Просмотр артефакта

Откройте трассировку в фирменном **[Trace Player](/docs/devtools/trace-player)** — интерфейсе WebdriverIO DevTools в специальном режиме плеера только для чтения:

```sh
show-trace trace-<sessionId>.zip          # бинарник в PATH после установки
npx show-trace trace-<sessionId>.zip      # или через npx
```

Плеер предоставляет путешествие во времени по DOM, вкладку A11y и оверлей выбора локатора, вкладку Transcript с функцией Copy-for-LLM, вкладки панели Errors / Console / Network / Source и временную шкалу с перемоткой. Тот же переносимый `.zip` также открывается в других автономных просмотрщиках трассировок и во встроенном просмотрщике отчёта Allure. Полное руководство, возможности и сочетания клавиш смотрите на странице **[Trace Player](/docs/devtools/trace-player)**.

## Узнать больше
Бинарник `show-trace`, поставляемый каждым адаптером, открывает тот же архив в плеере DevTools, который дополнительно предоставляет **вкладку A11y**: дерево доступности, зафиксированное для каждого действия, где щелчок по строке копирует локатор этого элемента.

Эти локаторы записываются на собственном диалекте раннера, сделавшего запись, поэтому их можно вставить напрямую во фреймворк, создавший трассировку. Элемент, идентифицируемый только по тексту, — это `a*=Logout` в WebdriverIO и `//a[contains(., "Logout")]` в Selenium — с подписью вызова, который его разрешает, `By.xpath()`. Nightwatch предпочитает нативный CSS-локатор, например `button[type="submit"]`, поскольку это единственный раннер, который читает голую строку селектора со стратегией CSS по умолчанию, и прибегает к XPath (с подписью `useXpath()` / `locateStrategy: 'xpath'`) только когда уникального CSS-локатора не существует. Все остальные локаторы — переносимый CSS.

Для использования LLM / агентами читайте `transcript.md` напрямую — это компактное Markdown-представление действий с селекторами и значениями.
