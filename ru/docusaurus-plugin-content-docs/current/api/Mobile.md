# Введение в пользовательские и расширенные мобильные команды в WebdriverIO

Тестирование мобильных приложений и мобильных веб-приложений сопряжено с определёнными трудностями, особенно когда речь идёт о платформенных различиях между Android и iOS. Хотя Appium предоставляет гибкость для обработки этих различий, часто приходится глубоко погружаться в сложную платформозависимую документацию ([Android](https://github.com/appium/appium-uiautomator2-driver/blob/master/docs/android-mobile-gestures.md), [iOS](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/)) и команды. Из-за этого написание тестовых скриптов становится более трудоёмким, подверженным ошибкам и сложным в поддержке.

Чтобы упростить этот процесс, WebdriverIO предлагает **пользовательские и расширенные мобильные команды**, разработанные специально для тестирования мобильных веб-приложений и нативных приложений. Эти команды скрывают сложности базовых API Appium, позволяя писать лаконичные, интуитивно понятные и платформонезависимые тестовые скрипты. Делая акцент на простоте использования, мы стремимся снизить дополнительную нагрузку при разработке скриптов Appium и дать вам возможность без труда автоматизировать мобильные приложения.

## Зачем нужны пользовательские мобильные команды?

### 1. **Упрощение сложных API**
Некоторые команды Appium, например жесты или взаимодействие с элементами, имеют многословный и запутанный синтаксис. Например, для выполнения долгого нажатия с помощью нативного API Appium необходимо вручную построить цепочку `action`:

```ts
const element = $('~Contacts')

await browser
    .action( 'pointer', { parameters: { pointerType: 'touch' } })
    .move({ origin: element })
    .down()
    .pause(1500)
    .up()
    .perform()
```

С пользовательскими командами WebdriverIO то же самое действие можно выполнить одной выразительной строкой кода:

```ts
await $('~Contacts').longPress();
```

Это значительно сокращает объём шаблонного кода, делая ваши скрипты чище и понятнее.

### 2. **Кроссплатформенная абстракция**
Мобильные приложения часто требуют платформозависимой обработки. Например, прокрутка в нативных приложениях существенно различается на [Android](https://github.com/appium/appium-uiautomator2-driver/blob/master/docs/android-mobile-gestures.md#mobile-scrollgesture) и [iOS](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/#mobile-scroll). WebdriverIO устраняет этот разрыв, предоставляя унифицированные команды, такие как `scrollIntoView()`, которые без проблем работают на всех платформах независимо от базовой реализации.

```ts
await $('~element').scrollIntoView();
```

Эта абстракция обеспечивает переносимость ваших тестов и избавляет от необходимости постоянно использовать ветвления или условную логику для учёта различий между ОС.

### 3. **Повышение продуктивности**
Уменьшая необходимость разбираться в низкоуровневых командах Appium и реализовывать их, мобильные команды WebdriverIO позволяют сосредоточиться на тестировании функциональности приложения, а не на борьбе с особенностями платформ. Это особенно полезно для команд с ограниченным опытом в мобильной автоматизации или тех, кто стремится ускорить цикл разработки.

### 4. **Согласованность и удобство поддержки**
Пользовательские команды привносят единообразие в ваши тестовые скрипты. Вместо различных реализаций схожих действий ваша команда может полагаться на стандартизированные, многократно используемые команды. Это не только упрощает поддержку кодовой базы, но и снижает порог входа для новых членов команды.

## Зачем расширять некоторые мобильные команды?

### 1. Добавление гибкости
Некоторые мобильные команды расширены, чтобы предоставить дополнительные опции и параметры, недоступные в стандартных API Appium. Например, WebdriverIO добавляет логику повторных попыток, тайм-ауты и возможность фильтровать webview по определённым критериям, обеспечивая больший контроль над сложными сценариями.

```ts
// Пример: настройка интервалов повторных попыток и тайм-аутов для обнаружения webview
await driver.getContexts({
  returnDetailedContexts: true,
  androidWebviewConnectionRetryTime: 1000, // Повтор каждую 1 секунду
  androidWebviewConnectTimeout: 10000,    // Тайм-аут через 10 секунд
});
```

Эти опции помогают адаптировать скрипты автоматизации к динамическому поведению приложения без дополнительного шаблонного кода.

### 2. Улучшение удобства использования
Расширенные команды скрывают сложности и повторяющиеся шаблоны, присущие нативным API. Они позволяют выполнять больше действий с меньшим количеством строк кода, снижая порог обучения для новых пользователей и делая скрипты проще для чтения и поддержки.

```ts
// Пример: расширенная команда для переключения контекста по заголовку
await driver.switchContext({
  title: 'My Webview Title',
});
```

По сравнению со стандартными методами Appium, расширенные команды избавляют от дополнительных шагов, таких как ручное получение доступных контекстов и их фильтрация.

### 3. Стандартизация поведения
WebdriverIO гарантирует, что расширенные команды ведут себя одинаково на разных платформах, таких как Android и iOS. Эта кроссплатформенная абстракция сводит к минимуму необходимость в условных ветвлениях в зависимости от операционной системы, что делает тестовые скрипты более удобными в поддержке.

```ts
// Пример: унифицированная команда прокрутки для обеих платформ
await $('~element').scrollIntoView();
```

Такая стандартизация упрощает кодовую базу, особенно для команд, автоматизирующих тесты на нескольких платформах.

### 4. Повышение надёжности
Благодаря механизмам повторных попыток, разумным значениям по умолчанию и подробным сообщениям об ошибках расширенные команды снижают вероятность нестабильных тестов. Эти улучшения делают ваши тесты устойчивыми к таким проблемам, как задержки при инициализации webview или переходные состояния приложения.

```ts
// Пример: расширенное переключение webview с надёжной логикой сопоставления
await driver.switchContext({
  url: /.*my-app\/dashboard/,
  androidWebviewConnectionRetryTime: 500,
  androidWebviewConnectTimeout: 7000,
});
```

Это делает выполнение тестов более предсказуемым и менее подверженным сбоям, вызванным факторами окружения.

### 5. Расширение возможностей отладки
Расширенные команды часто возвращают более богатые метаданные, что упрощает отладку сложных сценариев, особенно в гибридных приложениях. Например, такие команды, как getContext и getContexts, могут возвращать подробную информацию о webview, включая заголовок, URL и статус видимости.

```ts
// Пример: получение подробных метаданных для отладки
const contexts = await driver.getContexts({ returnDetailedContexts: true });
console.log(contexts);
```

Эти метаданные помогают быстрее выявлять и устранять проблемы, улучшая общий процесс отладки.


Расширяя мобильные команды, WebdriverIO не только упрощает автоматизацию, но и следует своей миссии — предоставлять разработчикам мощные, надёжные и интуитивно понятные инструменты.

## Гибридные приложения

Гибридные приложения сочетают веб-контент с нативной функциональностью и требуют особого подхода при автоматизации. Такие приложения используют webview для отображения веб-контента внутри нативного приложения. WebdriverIO предоставляет расширенные методы для эффективной работы с гибридными приложениями.

### Что такое webview
Webview — это браузероподобный компонент, встроенный в нативное приложение:

- **Android:** Webview основаны на Chrome/System Webview и могут содержать несколько страниц (подобно вкладкам браузера). Для автоматизации взаимодействия с такими webview требуется ChromeDriver. Appium может автоматически определить необходимую версию ChromeDriver на основе версии System WebView или Chrome, установленной на устройстве, и автоматически загрузить её, если она ещё не доступна. Такой подход обеспечивает бесперебойную совместимость и сводит к минимуму ручную настройку. Обратитесь к [документации Appium UIAutomator2](https://github.com/appium/appium-uiautomator2-driver?tab=readme-ov-file#automatic-discovery-of-compatible-chromedriver), чтобы узнать, как Appium автоматически загружает нужную версию ChromeDriver.
- **iOS:** Webview работают на основе Safari (WebKit) и идентифицируются общими ID вида `WEBVIEW_{id}`.

### Трудности при работе с гибридными приложениями
1. Определение нужного webview среди нескольких вариантов.
2. Получение дополнительных метаданных, таких как заголовок, URL или имя пакета, для лучшего понимания контекста.
3. Обработка платформенных различий между Android и iOS.
4. Надёжное переключение на нужный контекст в гибридном приложении.

### Ключевые команды для гибридных приложений

#### 1. `getContext`
Получает текущий контекст сессии. По умолчанию ведёт себя как метод getContext в Appium, но может предоставлять подробную информацию о контексте, если включена опция `returnDetailedContext`. Подробнее см. [`getContext`](/docs/api/mobile/getContext)

#### 2. `getContexts`
Возвращает подробный список доступных контекстов, улучшая метод contexts из Appium. Это упрощает определение нужного webview для взаимодействия без вызова дополнительных команд для получения заголовка, URL или активного `bundleId|packageName`. Подробнее см. [`getContexts`](/docs/api/mobile/getContexts)

#### 3. `switchContext`
Переключается на определённый webview по имени, заголовку или URL. Обеспечивает дополнительную гибкость, например возможность использовать регулярные выражения для сопоставления. Подробнее см. [`switchContext`](/docs/api/mobile/switchContext)

### Ключевые возможности для гибридных приложений
1. Подробные метаданные: получение исчерпывающих сведений для отладки и надёжного переключения контекста.
2. Кроссплатформенная согласованность: унифицированное поведение для Android и iOS с бесшовной обработкой особенностей каждой платформы.
3. Настраиваемая логика повторных попыток (Android): настройка интервалов повторных попыток и тайм-аутов для обнаружения webview.


:::info Примечания и ограничения
- Android предоставляет дополнительные метаданные, такие как `packageName` и `webviewPageId`, тогда как iOS ориентирован на `bundleId`.
- Логика повторных попыток настраивается для Android, но не применима к iOS.
- Существует ряд случаев, когда iOS не может найти webview. Appium предоставляет различные дополнительные capabilities для `appium-xcuitest-driver`, позволяющие найти webview. Если вы считаете, что webview не обнаруживается, попробуйте установить одну из следующих capabilities:
    - `appium:includeSafariInWebviews`: добавляет веб-контексты Safari в список контекстов, доступных во время теста нативного/webview-приложения. Это полезно, если тест открывает Safari и должен иметь возможность взаимодействовать с ним. По умолчанию `false`.
    - `appium:webviewConnectRetries`: максимальное количество повторных попыток, прежде чем отказаться от обнаружения страниц webview. Задержка между попытками составляет 500 мс, по умолчанию — `10` попыток.
    - `appium:webviewConnectTimeout`: максимальное время в миллисекундах ожидания обнаружения страницы webview. По умолчанию — `5000` мс.

Расширенные примеры и подробности смотрите в документации по мобильному API WebdriverIO.
:::
