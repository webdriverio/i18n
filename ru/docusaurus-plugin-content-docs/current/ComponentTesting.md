С помощью [Browser Runner](/docs/runner#browser-runner) в WebdriverIO вы можете запускать тесты в настоящем десктопном или мобильном браузере, используя WebdriverIO и протокол WebDriver для автоматизации и взаимодействия с тем, что отображается на странице. Этот подход имеет [много преимуществ](/docs/runner#browser-runner) по сравнению с другими тестовыми фреймворками, которые позволяют тестировать только с использованием [JSDOM](https://www.npmjs.com/package/jsdom).

## Поддержка браузеров

Браузерный раннер выполняет тестовый бандл в браузере. Этот бандл работает в Chrome 90, Edge 90, Firefox 90 и Safari 14.1, а также в более поздних версиях этих браузеров.

Сквозные (end-to-end) тесты выполняются в Node.js. Код, переданный в [`browser.execute`](/docs/api/browser/execute), напротив, выполняется в автоматизируемом браузере, который может быть старше указанных выше версий. Пишите такой код в рамках ES2021.

## Как это работает?

Browser Runner использует [Vite](https://vitejs.dev/) для рендеринга тестовой страницы и инициализации тестового фреймворка, чтобы запускать ваши тесты в браузере. В настоящее время поддерживается только Mocha, но Jasmine и Cucumber [есть в планах](https://github.com/orgs/webdriverio/projects/1). Это позволяет тестировать любые компоненты, даже в проектах, которые не используют Vite.

Сервер Vite запускается тестраннером WebdriverIO и настраивается так, чтобы вы могли использовать все репортеры и сервисы так же, как привыкли в обычных e2e-тестах. Кроме того, он инициализирует экземпляр [`browser`](/docs/api/browser), который предоставляет доступ к подмножеству [WebdriverIO API](/docs/api) для взаимодействия с любыми элементами на странице. Как и в e2e-тестах, вы можете получить доступ к этому экземпляру через переменную `browser`, доступную в глобальной области видимости, или импортировав его из `@wdio/globals`, в зависимости от значения параметра [`injectGlobals`](/docs/api/globals).

WebdriverIO имеет встроенную поддержку следующих фреймворков:

- [__Nuxt__](https://nuxt.com/): тестраннер WebdriverIO обнаруживает приложение Nuxt, автоматически настраивает composables вашего проекта и помогает замокать бэкенд Nuxt. Подробнее читайте в [документации по Nuxt](/docs/component-testing/vue#testing-vue-components-in-nuxt)
- [__TailwindCSS__](https://tailwindcss.com/): тестраннер WebdriverIO определяет, используете ли вы TailwindCSS, и корректно загружает окружение на тестовую страницу

## Настройка

Чтобы настроить WebdriverIO для модульного или компонентного тестирования в браузере, создайте новый проект WebdriverIO с помощью:

```bash
npm init wdio@latest ./
# or
yarn create wdio ./
```

Когда запустится мастер настройки, выберите `browser` для запуска модульного и компонентного тестирования и при желании выберите один из пресетов; в противном случае выберите _"Other"_, если вы хотите запускать только базовые модульные тесты. Вы также можете указать собственную конфигурацию Vite, если уже используете Vite в своем проекте. Дополнительную информацию смотрите во всех [опциях раннера](/docs/runner#runner-options).

:::info

__Примечание:__ по умолчанию WebdriverIO запускает браузерные тесты в CI в headless-режиме, например, если переменная окружения `CI` установлена в `'1'` или `'true'`. Вы можете вручную настроить это поведение с помощью опции раннера [`headless`](/docs/runner#headless).

:::

В конце этого процесса у вас должен появиться файл `wdio.conf.js`, содержащий различные настройки WebdriverIO, включая свойство `runner`, например:

```ts reference useHTTPS
https://github.com/webdriverio/example-recipes/blob/fd54f94306ed8e7b40f967739164dfe4d6d76b41/wdio.comp.conf.js
```

Определив различные [capabilities](/docs/configuration#capabilities), вы можете запускать тесты в разных браузерах, при желании — параллельно.

## Тестовая обвязка

Что запускать в тестах и как рендерить компоненты — полностью решать вам. Однако мы рекомендуем использовать [Testing Library](https://testing-library.com/) в качестве вспомогательного фреймворка, так как он предоставляет плагины для различных компонентных фреймворков, таких как React, Preact, Svelte и Vue. Он очень удобен для рендеринга компонентов на тестовой странице и автоматически удаляет эти компоненты после каждого теста.

Вы можете сочетать примитивы Testing Library с командами WebdriverIO как угодно, например:

```js reference useHTTPS
https://github.com/webdriverio/example-recipes/blob/fd54f94306ed8e7b40f967739164dfe4d6d76b41/component-testing/svelte-example.js
```

__Примечание:__ использование методов рендеринга из Testing Library помогает удалять созданные компоненты между тестами. Если вы не используете Testing Library, убедитесь, что прикрепляете тестовые компоненты к контейнеру, который очищается между тестами.

## Скрипты настройки

Вы можете подготовить тесты, запуская произвольные скрипты в Node.js или в браузере, например, для внедрения стилей, мокирования браузерных API или подключения к стороннему сервису. [Хуки](/docs/configuration#hooks) WebdriverIO можно использовать для выполнения кода в Node.js, а [`mochaOpts.require`](/docs/frameworks#require) позволяет импортировать скрипты в браузер до загрузки тестов, например:

```js wdio.conf.js
export const config = {
    // ...
    mochaOpts: {
        ui: 'tdd',
        // предоставьте скрипт настройки для запуска в браузере
        require: './__fixtures__/setup.js'
    },
    before: () => {
        // настройте тестовое окружение в Node.js
    }
    // ...
}
```

Например, если вы хотите замокать все вызовы [`fetch()`](https://developer.mozilla.org/en-US/docs/Web/API/fetch) в своем тесте, используйте следующий скрипт настройки:

```js ./fixtures/setup.js
import { fn } from '@wdio/browser-runner'

// выполнить код до загрузки всех тестов
window.fetch = fn()

export const mochaGlobalSetup = () => {
    // выполнить код после загрузки тестового файла
}

export const mochaGlobalTeardown = () => {
    // выполнить код после выполнения spec-файла
}

```

Теперь в своих тестах вы можете задавать собственные значения ответов для всех запросов браузера. Подробнее о глобальных фикстурах читайте в [документации Mocha](https://mochajs.org/#global-fixtures).

## Отслеживание изменений в тестах и файлах приложения

Существует несколько способов отладки браузерных тестов. Самый простой — запустить тестраннер WebdriverIO с флагом `--watch`, например:

```sh
$ npx wdio run ./wdio.conf.js --watch
```

Сначала будут выполнены все тесты, после чего выполнение приостановится. Затем вы можете вносить изменения в отдельные файлы, которые будут перезапускаться по отдельности. Если вы зададите [`filesToWatch`](/docs/configuration#filestowatch), указывающий на файлы вашего приложения, то при изменениях в приложении будут перезапускаться все тесты.

## Отладка

Хотя (пока) невозможно устанавливать точки останова в IDE так, чтобы они распознавались удаленным браузером, вы можете использовать команду [`debug`](/docs/api/browser/debug), чтобы остановить тест в любой момент. Это позволяет открыть DevTools и отлаживать тест, устанавливая точки останова на [вкладке Sources](https://buddy.works/tutorials/debugging-javascript-efficiently-with-chrome-devtools).

При вызове команды `debug` в терминале также откроется интерфейс Node.js REPL со следующим сообщением:

```
The execution has stopped!
You can now go into the browser or use the command line as REPL
(To exit, press ^C again or type .exit)
```

Нажмите `Ctrl` или `Command` + `c` либо введите `.exit`, чтобы продолжить выполнение теста.

## Запуск с использованием Selenium Grid

Если у вас настроен [Selenium Grid](https://www.selenium.dev/documentation/grid/) и вы запускаете браузер через него, необходимо задать опцию браузерного раннера `host`, чтобы браузер мог обратиться к нужному хосту, на котором раздаются тестовые файлы, например:

```ts title=wdio.conf.ts
export const config: WebdriverIO.Config = {
    runner: ['browser', {
        // сетевой IP-адрес машины, на которой запущен процесс WebdriverIO
        host: 'http://172.168.0.2'
    }]
}
```

Это гарантирует, что браузер откроет правильный экземпляр сервера, размещенный на машине, где выполняются тесты WebdriverIO.
