С помощью тестраннера WebdriverIO вы можете перезапускать определённые тесты, которые оказываются нестабильными из-за таких факторов, как ненадёжная сеть или состояния гонки. (Однако не рекомендуется просто увеличивать количество перезапусков, если тесты становятся нестабильными!)

## Перезапуск наборов тестов в Mocha

Начиная с версии 3 Mocha, вы можете перезапускать целые наборы тестов (всё, что находится внутри блока `describe`). Если вы используете Mocha, вам следует отдать предпочтение этому механизму повторных запусков вместо реализации WebdriverIO, которая позволяет перезапускать только отдельные тестовые блоки (всё, что находится внутри блока `it`). Чтобы использовать метод `this.retries()`, блок набора `describe` должен использовать несвязанную функцию `function(){}` вместо стрелочной функции `() => {}`, как описано в [документации Mocha](https://mochajs.org/#arrow-functions). В Mocha вы также можете задать количество повторных запусков для всех спецификаций с помощью `mochaOpts.retries` в вашем `wdio.conf.js`.

Вот пример:

```js
describe('retries', function () {
    // Повторять все тесты в этом наборе до 4 раз
    this.retries(4)

    beforeEach(async () => {
        await browser.url('http://www.yahoo.com')
    })

    it('should succeed on the 3rd try', async function () {
        // Указать, что этот тест нужно повторять не более 2 раз
        this.retries(2)
        console.log('run')
        await expect($('.foo')).toBeDisplayed()
    })
})
```

## Перезапуск отдельных тестов в Jasmine или Mocha

Чтобы перезапустить определённый тестовый блок, просто передайте количество перезапусков в качестве последнего параметра после функции тестового блока:

  values={[

    {label: 'Jasmine', value: 'jasmine'},

```js
describe('my flaky app', () => {
    /**
     * спецификация, которая выполняется максимум 4 раза (1 основной запуск + 3 перезапуска)
     */
    it('should rerun a test at least 3 times', async function () {
        console.log(this.wdioRetries) // возвращает количество повторных запусков
        // ...
    }, 3)
})
```

То же самое работает и для хуков:

```js
describe('my flaky app', () => {
    /**
     * хук, который выполняется максимум 2 раза (1 основной запуск + 1 перезапуск)
     */
    beforeEach(async () => {
        // ...
    }, 1)

    // ...
})
```

```js
describe('my flaky app', () => {
    /**
     * спецификация, которая выполняется максимум 4 раза (1 основной запуск + 3 перезапуска)
     */
    it('should rerun a test at least 3 times', async function () {
        console.log(this.wdioRetries) // возвращает количество повторных запусков
        // ...
    }, jasmine.DEFAULT_TIMEOUT_INTERVAL, 3)

```

То же самое работает и для хуков:

```js

    /**
     * хук, который выполняется максимум 2 раза (1 основной запуск + 1 перезапуск)
     */
    beforeEach(async () => {
        // ...
    }, jasmine.DEFAULT_TIMEOUT_INTERVAL, 1)

    // ...
})
```

Если вы используете Jasmine, второй параметр зарезервирован для тайм-аута. Чтобы задать параметр повторных запусков, необходимо установить тайм-аут в значение по умолчанию `jasmine.DEFAULT_TIMEOUT_INTERVAL`, а затем указать количество повторных запусков.

</TabItem>
</Tabs>

Этот механизм повторных запусков позволяет повторять только отдельные хуки или тестовые блоки. Если ваш тест сопровождается хуком для настройки приложения, этот хук не запускается повторно. [Mocha предлагает](https://mochajs.org/#retry-tests) встроенные повторные запуски тестов, которые обеспечивают такое поведение, а Jasmine — нет. Получить количество выполненных повторных запусков можно в хуке `afterTest`.

## Повторные запуски в Cucumber

### Перезапуск полных наборов в Cucumber

Для cucumber >=6 вы можете указать параметр конфигурации [`retry`](https://github.com/cucumber/cucumber-js/blob/master/docs/cli.md#retry-failing-tests) вместе с необязательным параметром `retryTagFilter`, чтобы все или некоторые из ваших неудачных сценариев повторно запускались до тех пор, пока не будут успешно выполнены. Для работы этой функции необходимо установить `scenarioLevelReporter` в значение `true`.

### Перезапуск определений шагов в Cucumber

Чтобы задать количество перезапусков для определённых определений шагов, просто примените к ним параметр retry, например:

```js
export default function () {
    /**
     * определение шага, которое выполняется максимум 3 раза (1 основной запуск + 2 перезапуска)
     */
    this.Given(/^some step definition$/, { wrapperOptions: { retry: 2 } }, async () => {
        // ...
    })
    // ...
})
```

Перезапуски можно определить только в файле определений шагов, но никогда в feature-файле.

## Добавление повторных запусков на уровне файлов спецификаций

Ранее были доступны только повторные запуски на уровне тестов и наборов, чего в большинстве случаев достаточно.

Но в любых тестах, связанных с состоянием (например, на сервере или в базе данных), после первого сбоя теста состояние может остаться некорректным. У последующих повторных запусков может не быть шансов на успех из-за некорректного состояния, с которого они начнутся.

Для каждого файла спецификации создаётся новый экземпляр `browser`, что делает его идеальным местом для подключения хуков и настройки любых других состояний (сервер, базы данных). Повторные запуски на этом уровне означают, что весь процесс настройки будет просто повторён, как если бы это был новый файл спецификации.

```js title="wdio.conf.js"
export const config = {
    // ...
    /**
     * Количество повторных запусков всего файла спецификации, если он завершился неудачей целиком
     */
    specFileRetries: 1,
    /**
     * Задержка в секундах между попытками повторного запуска файла спецификации
     */
    specFileRetriesDelay: 0,
    /**
     * Повторно запускаемые файлы спецификаций вставляются в начало очереди и запускаются немедленно
     */
    specFileRetriesDeferred: false
}
```

## Многократный запуск определённого теста

Это помогает предотвратить появление нестабильных тестов в кодовой базе. Если добавить параметр командной строки `--repeat`, указанные спецификации или наборы будут запущены N раз. При использовании этого флага также необходимо указать флаг `--spec` или `--suite`.

При добавлении новых тестов в кодовую базу, особенно через процесс CI/CD, тесты могут пройти и быть влиты, но позже стать нестабильными. Эта нестабильность может быть вызвана разными причинами, такими как проблемы с сетью, нагрузка на сервер, размер базы данных и т. д. Использование флага `--repeat` в вашем процессе CD/CD может помочь выявить такие нестабильные тесты до того, как они будут влиты в основную кодовую базу.

Одна из стратегий — запускать тесты как обычно в процессе CI/CD, но если вы добавляете новый тест, вы можете запустить дополнительный набор тестов с новой спецификацией, указанной в `--spec`, вместе с `--repeat`, чтобы новый тест был выполнен x раз. Если тест завершится неудачей хотя бы один раз, он не будет влит, и нужно будет разобраться, почему он упал.

```sh
# Это запустит спецификацию example.e2e.js 5 раз
npx wdio run ./wdio.conf.js --spec example.e2e.js --repeat 5
```
