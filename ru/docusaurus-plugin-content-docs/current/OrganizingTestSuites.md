По мере роста проектов неизбежно добавляется всё больше интеграционных тестов. Это увеличивает время сборки и снижает продуктивность.

Чтобы этого избежать, следует запускать тесты параллельно. WebdriverIO уже тестирует каждую спецификацию (или _feature-файл_ в Cucumber) параллельно в рамках одной сессии. В целом старайтесь тестировать только одну функцию в одном файле спецификации. Старайтесь не размещать в одном файле слишком много или слишком мало тестов. (Впрочем, золотого правила здесь нет.)

Как только у ваших тестов появится несколько файлов спецификаций, стоит начать запускать их одновременно. Для этого настройте свойство `maxInstances` в вашем конфигурационном файле. WebdriverIO позволяет запускать тесты с максимальным параллелизмом — то есть независимо от того, сколько у вас файлов и тестов, все они могут выполняться параллельно. (Это всё же зависит от определённых ограничений, таких как процессор вашего компьютера, ограничения на параллелизм и т. д.)

> Допустим, у вас есть 3 разных capabilities (Chrome, Firefox и Safari), и вы установили `maxInstances` равным `1`. Тестраннер WDIO создаст 3 процесса. Следовательно, если у вас 10 файлов спецификаций и вы установили `maxInstances` равным `10`, _все_ файлы спецификаций будут протестированы одновременно, и будет создано 30 процессов.

Вы можете определить свойство `maxInstances` глобально, чтобы задать этот атрибут для всех браузеров.

Если вы используете собственный WebDriver grid, у вас может быть (например) больше ресурсов для одного браузера, чем для другого. В этом случае вы можете _ограничить_ `maxInstances` в объекте capability:

```js
// wdio.conf.js
export const config = {
    // ...
    // set maxInstance for all browser
    maxInstances: 10,
    // ...
    capabilities: [{
        browserName: 'firefox'
    }, {
        // maxInstances can get overwritten per capability. So if you have an in-house WebDriver
        // grid with only 5 firefox instance available you can make sure that not more than
        // 5 instance gets started at a time.
        browserName: 'chrome'
    }],
    // ...
}
```

## Наследование от основного конфигурационного файла

Если вы запускаете набор тестов в нескольких окружениях (например, dev и integration), может быть полезно использовать несколько конфигурационных файлов, чтобы всё оставалось управляемым.

Подобно [концепции page object](pageobjects), первое, что вам понадобится, — это основной конфигурационный файл. Он содержит все настройки, общие для всех окружений.

Затем создайте отдельный конфигурационный файл для каждого окружения и дополните основную конфигурацию настройками, специфичными для окружения:

```js
// wdio.dev.config.js
import { deepmerge } from 'deepmerge-ts'
import wdioConf from './wdio.conf.js'

// have main config file as default but overwrite environment specific information
export const config = deepmerge(wdioConf.config, {
    capabilities: [
        // more caps defined here
        // ...
    ],

    // run tests on sauce instead locally
    user: process.env.SAUCE_USERNAME,
    key: process.env.SAUCE_ACCESS_KEY,
    services: ['sauce']
}, { clone: false })

// add an additional reporter
config.reporters.push('allure')
```

## Группировка спецификаций в наборы

Вы можете группировать спецификации тестов в наборы (suites) и запускать отдельные конкретные наборы вместо всех сразу.

Сначала определите наборы в конфигурации WDIO:

```js
// wdio.conf.js
export const config = {
    // define all tests
    specs: ['./test/specs/**/*.spec.js'],
    // ...
    // define specific suites
    suites: {
        login: [
            './test/specs/login.success.spec.js',
            './test/specs/login.failure.spec.js'
        ],
        otherFeature: [
            // ...
        ]
    },
    // ...
}
```

Теперь, если вы хотите запустить только один набор, вы можете передать имя набора в качестве аргумента CLI:

```sh
wdio wdio.conf.js --suite login
```

Или запустить несколько наборов одновременно:

```sh
wdio wdio.conf.js --suite login --suite otherFeature
```

## Группировка спецификаций для последовательного запуска

Как описано выше, параллельный запуск тестов имеет свои преимущества. Однако бывают случаи, когда полезно сгруппировать тесты для последовательного запуска в одном экземпляре. В основном это ситуации с большими затратами на подготовку, например транспиляция кода или развёртывание облачных экземпляров, но существуют и продвинутые сценарии использования, которые выигрывают от этой возможности.

Чтобы сгруппировать тесты для запуска в одном экземпляре, определите их как массив внутри определения specs.

```json
    "specs": [
        [
            "./test/specs/test_login.js",
            "./test/specs/test_product_order.js",
            "./test/specs/test_checkout.js"
        ],
        "./test/specs/test_b*.js",
    ],
```
В приведённом выше примере тесты 'test_login.js', 'test_product_order.js' и 'test_checkout.js' будут запущены последовательно в одном экземпляре, а каждый из тестов "test_b*" будет запущен параллельно в отдельных экземплярах.

Также можно группировать спецификации, определённые в наборах, поэтому теперь вы можете определять наборы так:
```json
    "suites": {
        end2end: [
            [
                "./test/specs/test_login.js",
                "./test/specs/test_product_order.js",
                "./test/specs/test_checkout.js"
            ]
        ],
        allb: ["./test/specs/test_b*.js"]
},
```
и в этом случае все тесты набора "end2end" будут запущены в одном экземпляре.

При последовательном запуске тестов с использованием шаблона файлы спецификаций будут запускаться в алфавитном порядке

```json
  "suites": {
    end2end: ["./test/specs/test_*.js"]
  },
```

Это запустит файлы, соответствующие приведённому выше шаблону, в следующем порядке:

```
  [
      "./test/specs/test_checkout.js",
      "./test/specs/test_login.js",
      "./test/specs/test_product_order.js"
  ]
```

## Запуск выбранных тестов

В некоторых случаях вам может понадобиться выполнить только один тест (или подмножество тестов) из ваших наборов.

С помощью параметра `--spec` вы можете указать, какой _набор_ (Mocha, Jasmine) или _feature_ (Cucumber) следует запустить. Путь разрешается относительно текущего рабочего каталога.

Например, чтобы запустить только тест входа в систему:

```sh
wdio wdio.conf.js --spec ./test/specs/e2e/login.js
```

Или запустить несколько спецификаций одновременно:

```sh
wdio wdio.conf.js --spec ./test/specs/signup.js --spec ./test/specs/forgot-password.js
```

Если значение `--spec` не указывает на конкретный файл спецификации, оно используется для фильтрации имён файлов спецификаций, определённых в вашей конфигурации.

Чтобы запустить все спецификации, в именах файлов которых есть слово «dialog», можно использовать:

```sh
wdio wdio.conf.js --spec dialog
```

Обратите внимание, что каждый тестовый файл выполняется в отдельном процессе тестраннера. Поскольку мы не сканируем файлы заранее (см. следующий раздел для информации о передаче имён файлов в `wdio` через конвейер), вы _не можете_ использовать (например) `describe.only` в начале файла спецификации, чтобы указать Mocha запустить только этот набор.

Эта функция поможет вам достичь той же цели.

Если указана опция `--spec`, она переопределит любые шаблоны, заданные в параметре конфигурации `specs` или в `wdio:specs` capability.

## Исключение выбранных тестов

При необходимости, если нужно исключить определённые файлы спецификаций из запуска, вы можете использовать параметр `--exclude` (Mocha, Jasmine) или feature (Cucumber).

Например, чтобы исключить тест входа в систему из запуска:

```sh
wdio wdio.conf.js --exclude ./test/specs/e2e/login.js
```

Или исключить несколько файлов спецификаций:

 ```sh
wdio wdio.conf.js --exclude ./test/specs/signup.js --exclude ./test/specs/forgot-password.js
```

Или исключить файл спецификации при фильтрации с использованием набора:

```sh
wdio wdio.conf.js --suite login --exclude ./test/specs/e2e/login.js
```

Если значение `--exclude` не указывает на конкретный файл спецификации, оно используется для фильтрации имён файлов спецификаций, определённых в вашей конфигурации.

Чтобы исключить все спецификации, в именах файлов которых есть слово «dialog», можно использовать:

```sh
wdio wdio.conf.js --exclude dialog
```

### Исключение целого набора

Вы также можете исключить целый набор по имени. Если значение исключения совпадает с именем набора, определённого в вашей конфигурации, и не похоже на путь к файлу, весь набор будет пропущен:

```sh
wdio wdio.conf.js --suite login --suite checkout --exclude login
```

Это запустит только набор `checkout`, полностью пропустив набор `login`.

Смешанные исключения (наборы и шаблоны спецификаций) работают как ожидается:

```sh
wdio wdio.conf.js --suite login --exclude dialog --exclude signup
```

В этом примере, если `signup` — это имя определённого набора, этот набор будет исключён. Шаблон `dialog` отфильтрует все файлы спецификаций, содержащие «dialog» в имени файла.

:::note
Если вы укажете одновременно `--suite X` и `--exclude X`, исключение имеет приоритет, и набор `X` не будет запущен.
:::

Если указана опция `--exclude`, она переопределит любые шаблоны, заданные в параметре конфигурации `exclude` или в `wdio:exclude` capability.

## Запуск наборов и спецификаций

Запустите целый набор вместе с отдельными спецификациями.

```sh
wdio wdio.conf.js --suite login --spec ./test/specs/signup.js
```

## Запуск нескольких конкретных спецификаций

Иногда — в контексте непрерывной интеграции и не только — необходимо указать несколько наборов спецификаций для запуска. Утилита командной строки `wdio` в WebdriverIO принимает имена файлов, переданные через конвейер (из `find`, `grep` и других).

Имена файлов, переданные через конвейер, переопределяют список glob-шаблонов или имён файлов, указанных в списке `spec` конфигурации.

```sh
grep -r -l --include "*.js" "myText" | wdio wdio.conf.js
```

_**Примечание:** Это_ не _переопределяет флаг `--spec` для запуска одной спецификации._

## Запуск определённых тестов с помощью MochaOpts

Вы также можете отфильтровать, какие конкретные `suite|describe` и/или `it|test` следует запустить, передав специфичный для Mocha аргумент `--mochaOpts.grep` в CLI wdio.

```sh
wdio wdio.conf.js --mochaOpts.grep myText
wdio wdio.conf.js --mochaOpts.grep "Text with spaces"
```

_**Примечание:** Mocha фильтрует тесты после того, как тестраннер WDIO создаст экземпляры, поэтому вы можете увидеть, что несколько экземпляров создаются, но фактически не выполняются._

## Исключение определённых тестов с помощью MochaOpts

Вы также можете отфильтровать, какие конкретные `suite|describe` и/или `it|test` следует исключить, передав специфичный для Mocha аргумент `--mochaOpts.invert` в CLI wdio. `--mochaOpts.invert` выполняет действие, противоположное `--mochaOpts.grep`

```sh
wdio wdio.conf.js --mochaOpts.grep "string|regex" --mochaOpts.invert
wdio wdio.conf.js --spec ./test/specs/e2e/login.js --mochaOpts.grep "string|regex" --mochaOpts.invert
```

_**Примечание:** Mocha фильтрует тесты после того, как тестраннер WDIO создаст экземпляры, поэтому вы можете увидеть, что несколько экземпляров создаются, но фактически не выполняются._

## Остановка тестирования после сбоя

С помощью опции `bail` вы можете указать WebdriverIO прекратить тестирование после падения любого теста.

Это полезно при больших наборах тестов, когда вы уже знаете, что сборка сломается, но хотите избежать долгого ожидания полного прогона тестов.

Опция `bail` ожидает число, которое указывает, сколько падений тестов может произойти, прежде чем WebDriver остановит весь прогон тестов. По умолчанию значение равно `0`, что означает, что всегда запускаются все найденные спецификации тестов.

Дополнительную информацию о настройке bail см. на [странице опций](configuration).
## Иерархия параметров запуска

При указании спецификаций для запуска существует определённая иерархия, определяющая, какой шаблон имеет приоритет. В настоящее время она работает так, от наивысшего приоритета к наименьшему:

> CLI-аргумент `--spec` > capability `wdio:specs` > конфигурация `specs`
> CLI-аргумент `--exclude` > конфигурация `exclude` > capability `wdio:exclude`

Если задан только параметр конфигурации, он будет использоваться для всех capabilities. Однако если шаблон определён на уровне capability, он будет использоваться вместо шаблона конфигурации. Наконец, любой шаблон спецификаций, заданный в командной строке, переопределит все остальные заданные шаблоны.

### Использование шаблонов спецификаций, заданных в capability

Когда вы определяете шаблон спецификаций на уровне capability, он переопределяет любые шаблоны, заданные на уровне конфигурации. Это полезно, когда нужно разделять тесты в зависимости от различающихся capabilities устройств. В таких случаях удобнее использовать общий шаблон спецификаций на уровне конфигурации и более конкретные шаблоны на уровне capability.

Например, предположим, что у вас есть два каталога: один для тестов Android и один для тестов iOS.

Ваш конфигурационный файл может определять шаблон для тестов, не привязанных к конкретному устройству, следующим образом:

```js
{
    specs: ['tests/general/**/*.js']
}
```

но при этом у вас будут разные capabilities для устройств Android и iOS, где шаблоны могут выглядеть так:

```json
{
  "platformName": "Android",
  "wdio:specs": [
    "tests/android/**/*.js"
  ]
}
```

```json
{
  "platformName": "iOS",
  "wdio:specs": [
    "tests/ios/**/*.js"
  ]
}
```

Если вам нужны обе эти capabilities в конфигурационном файле, то устройство Android будет запускать только тесты из пространства имён "android", а устройство iOS — только тесты из пространства имён "ios"!

```js
//wdio.conf.js
export const config = {
    "specs": [
        "tests/general/**/*.js"
    ],
    "capabilities": [
        {
            platformName: "Android",
            "wdio:specs": ["tests/android/**/*.js"],
            //...
        },
        {
            platformName: "iOS",
            "wdio:specs": ["tests/ios/**/*.js"],
            //...
        },
        {
            platformName: "Chrome",
            //config level specs will be used
        }
    ]
}
```
