Из-за изменений в V8 команда WebdriverIO [объявила](https://webdriver.io/blog/2021/07/28/sync-api-deprecation) о прекращении поддержки синхронного выполнения команд к апрелю 2023 года. Команда усердно работала над тем, чтобы сделать переход максимально простым. В этом руководстве мы объясняем, как можно постепенно перевести ваш набор тестов с синхронного режима на асинхронный. В качестве примера мы используем [Cucumber Boilerplate](https://github.com/webdriverio/cucumber-boilerplate), но подход точно такой же и для всех других проектов.

## Промисы в JavaScript

Синхронное выполнение было популярно в WebdriverIO, потому что оно избавляет от сложностей, связанных с промисами. Особенно если вы пришли из других языков, где эта концепция не существует в таком виде, поначалу это может сбивать с толку. Однако промисы — очень мощный инструмент для работы с асинхронным кодом, и современный JavaScript делает работу с ними действительно простой. Если вы никогда не работали с промисами, рекомендуем ознакомиться с [справочным руководством MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise), так как объяснение этой темы выходит за рамки данного руководства.

## Переход на асинхронный режим

Тестраннер WebdriverIO может обрабатывать асинхронное и синхронное выполнение в рамках одного набора тестов. Это означает, что вы можете постепенно, шаг за шагом и в своём темпе, переводить свои тесты и PageObjects. Например, в Cucumber Boilerplate определён [большой набор определений шагов](https://github.com/webdriverio/cucumber-boilerplate/tree/main/src/support/action), которые вы можете скопировать в свой проект. Мы можем переводить по одному определению шага или по одному файлу за раз.

:::tip

WebdriverIO предлагает [codemod](https://github.com/webdriverio/codemod), который позволяет преобразовать ваш синхронный код в асинхронный почти полностью автоматически. Сначала запустите codemod, как описано в документации, а затем при необходимости используйте это руководство для ручной миграции.

:::

Во многих случаях всё, что нужно сделать, — это сделать функцию, в которой вы вызываете команды WebdriverIO, `async` и добавить `await` перед каждой командой. Взглянув на первый файл `clearInputField.ts`, который нужно преобразовать в проекте boilerplate, мы переходим от:

```ts
export default (selector: Selector) => {
    $(selector).clearValue();
};
```

к:

```ts
export default async (selector: Selector) => {
    await $(selector).clearValue();
};
```

Вот и всё. Полный коммит со всеми примерами переписывания можно посмотреть здесь:

#### Коммиты:

- _преобразование всех определений шагов_ [[af6625f]](https://github.com/webdriverio/cucumber-boilerplate/pull/481/commits/af6625fcd01dc087479e84562f237ecf38b3537d)

:::info
Этот переход не зависит от того, используете вы TypeScript или нет. Если вы используете TypeScript, просто убедитесь, что в итоге вы изменили свойство `types` в вашем `tsconfig.json` с `webdriverio/sync` на `@wdio/globals/types`. Также убедитесь, что цель компиляции установлена как минимум на `ES2018`.
:::

## Особые случаи

Конечно, всегда есть особые случаи, требующие немного большего внимания.

### Циклы ForEach

Если у вас есть цикл `forEach`, например для перебора элементов, нужно убедиться, что callback-функция итератора корректно обрабатывается асинхронно, например:

```js
const elems = $$('div')
elems.forEach((elem) => {
    elem.click()
})
```

Функция, которую мы передаём в `forEach`, является функцией-итератором. В синхронном мире она кликнула бы по всем элементам, прежде чем двигаться дальше. Если мы преобразуем это в асинхронный код, нам нужно убедиться, что мы дожидаемся завершения выполнения каждой функции-итератора. При добавлении `async`/`await` эти функции-итераторы будут возвращать промис, который нам нужно разрешить. Поэтому `forEach` больше не идеален для перебора элементов, так как он не возвращает результат функции-итератора — тот самый промис, которого нам нужно дождаться. Следовательно, нам нужно заменить `forEach` на `map`, который возвращает этот промис. `map`, а также все остальные методы-итераторы массивов, такие как `find`, `every`, `reduce` и другие, реализованы так, что учитывают промисы внутри функций-итераторов, и поэтому их использование в асинхронном контексте упрощено. Преобразованный пример выше выглядит так:

```js
const elems = await $$('div')
await elems.forEach((elem) => {
    return elem.click()
})
```

Например, чтобы получить все элементы `<h3 />` и их текстовое содержимое, можно выполнить:

```js
await browser.url('https://webdriver.io')

const h3Texts = await browser.$$('h3').map((img) => img.getText())
console.log(h3Texts);
/**
 * возвращает:
 * [
 *   'Extendable',
 *   'Compatible',
 *   'Feature Rich',
 *   'Who is using WebdriverIO?',
 *   'Support for Modern Web and Mobile Frameworks',
 *   'Google Lighthouse Integration',
 *   'Watch Talks about WebdriverIO',
 *   'Get Started With WebdriverIO within Minutes'
 * ]
 */
```

Если это выглядит слишком сложно, можно рассмотреть использование простых циклов for, например:

```js
const elems = await $$('div')
for (const elem of elems) {
    await elem.click()
}
```

`$$` возвращает [`ElementArray`](/docs/api/browser/$$). Вы также можете перебирать его до того, как дождётесь списка:

```js
for await (const elem of $$('div')) {
    await elem.click()
}
```

`for (const elem of $$('div'))` выбрасывает ошибку, пока список не будет разрешён, потому что синхронный цикл не может дождаться выполнения запроса. Сначала дождитесь списка, как в примере выше, или используйте `for await`.

### Утверждения WebdriverIO

Если вы используете вспомогательную библиотеку утверждений WebdriverIO [`expect-webdriverio`](https://webdriver.io/docs/api/expect-webdriverio), обязательно ставьте `await` перед каждым вызовом `expect`, например:

```ts
expect($('input')).toHaveAttribute('class', expect.stringContaining('form'))
```

нужно преобразовать в:

```ts
await expect($('input')).toHaveAttribute('class', expect.stringContaining('form'))
```

### Синхронные методы PageObject и асинхронные тесты

Если вы писали PageObjects в своём наборе тестов в синхронном стиле, вы больше не сможете использовать их в асинхронных тестах. Если вам нужно использовать метод PageObject как в синхронных, так и в асинхронных тестах, мы рекомендуем продублировать метод и предоставить его для обеих сред, например:

```js
class MyPageObject extends Page {
    /**
     * определение элементов
     */
    get btnStart () { return $('button=Start') }
    get loadedPage () { return $('#finish') }

    someMethod () {
        // синхронный код
    }

    someMethodAsync () {
        // асинхронная версия MyPageObject.someMethod()
    }
}
```

После завершения миграции вы можете удалить синхронные методы PageObject и навести порядок в именовании.

Если вы не хотите поддерживать две разные версии метода PageObject, вы также можете перевести весь PageObject на асинхронный режим и использовать [`browser.call`](https://webdriver.io/docs/api/browser/call) для выполнения метода в синхронной среде, например:

```js
// до:
// MyPageObject.someMethod()
// после:
browser.call(() => MyPageObject.someMethod())
```

Команда `call` гарантирует, что асинхронный `someMethod` будет разрешён, прежде чем перейти к следующей команде.

## Заключение

Как видно из [итогового PR с переписанным кодом](https://github.com/webdriverio/cucumber-boilerplate/pull/481/files), сложность такого переписывания довольно невелика. Помните, что вы можете переписывать по одному определению шага за раз. WebdriverIO прекрасно справляется с синхронным и асинхронным выполнением в рамках одного фреймворка.
